# 03 系统架构

## 结论

BlackRain 的目标架构是 **Electron 宿主 + React 界面 + Rust daemon + 原装 codex app-server**。Electron 提供桌面和 Browser 能力；Rust daemon 保留现有领域逻辑并监管内核；`codex-rs` 只负责 agent。

当前 HEAD 仍是 Tauri 实现。以下是目标分层，不是完成度声明。

## 目标拓扑

```text
BlackRain Electron
  ├─ Main process
  │   ├─ App/window lifecycle
  │   ├─ permission/download/update policy
  │   ├─ Browser backend / WebContentsView registry / session / CDP
  │   └─ Rust daemon supervisor
  ├─ Preload bridge
  │   └─ typed allowlisted IPC
  ├─ React renderer
  │   ├─ projects / threads / composer
  │   ├─ approvals / diff / terminal
  │   └─ Browser sidebar controls / bounds / state
  └─ blackrain_daemon
      ├─ shared domain cores
      ├─ original codex app-server
      ├─ dedicated CODEX_HOME
      └─ optional Model Gateway
```

## ① 原装 Codex 内核

- 来源：锁定的 OpenAI `codex-rs` 上游。
- 接口：`codex app-server` JSON-RPC 与事件流。
- 职责：thread、turn、工具调用、审批、停止、恢复和模型请求。
- 纪律：只读、只调用、不 fork agent loop、不叠加第二内核。

BlackRain 对内核的工作是版本锁、协议探针、能力盘点、构建和回归，不是改写。

## ② Rust daemon

daemon 是跨宿主的本地后端：

- 启停和监管 app-server
- 管理 App 专属 `CODEX_HOME`
- 提供项目、文件、Git、终端和已有 shared core
- 监管可选 Gateway
- 与 Electron main 使用可双向发起请求的本地 JSON-RPC
- 把 app-server 的 Browser tool request 转发给 Electron Browser backend
- 标准化事件和错误

迁移原则是把当前 Tauri App adapter 中可复用的逻辑收敛到 daemon/shared core，而不是迁入 Electron main。

## ③ Electron main 与 preload

Main 拥有所有桌面特权：

- BrowserWindow、WebContentsView、page WebContents、session、registry 与 CDP
- 菜单、通知、剪贴板和外部协议
- 权限、下载、弹窗和导航策略
- daemon 生命周期、退出顺序和崩溃恢复
- 打包、签名、更新和系统集成

Preload 只暴露显式类型化 API。renderer 不获得 Node.js、原始 IPC、daemon token 或任意文件系统能力。

## ④ React renderer

React renderer 负责用户可见产品，不承担特权和领域真源：

- 项目与 thread 导航
- 对话、队列、审批和恢复
- diff、终端、工具活动和错误呈现
- Browser chrome、状态和用户接管
- 设置、账号和模型选择

现有设计系统和状态编排可以迁移；Tauri 调用必须逐步替换为宿主无关客户端合同。

## ⑤ Codex 式 In-app Browser

BlackRain 高度采用三份本机研究稿确认的 Codex App Browser 功能与控制面，而不是建立独立 Playwright/headless agent browser。嵌入原语使用 Electron 当前推荐、由 main 直接持有的 `WebContentsView`：

```text
Codex thread / app-server Browser tool request
  -> Rust daemon
  -> authenticated Browser RPC
  -> Electron main BrowserBackend
  -> BrowserRegistry / BrowserViewManager
  -> main-owned WebContentsView
  -> page WebContents
  -> Electron API / Chromium CDP
```

main 创建每个 `WebContentsView`，在创建时固定 partition、sandbox、Node off、context isolation、web security 和无 preload，再把 view 加入 Browser registry。renderer 只通过类型化 IPC 上报 sidebar bounds、visibility、active tab、窗口 generation 和 modal/遮挡状态，不能创建页面 WebContents 或提供任意 partition、preload、CDP method。

main 维护以下不同标识，禁止混用：

```text
appSessionId -> ownerWindowId -> threadId/routeKey -> browserTabId -> apiTabId
             -> viewId/viewGeneration -> webContentsId -> CDP target/session
```

Browser 的关键合同：

- P0 使用 App 专属持久 partition `persist:blackrain-browser-app` 保存登录态。
- 网页不加载 BlackRain preload，不能看到 Node、IPC、daemon endpoint 或 token。
- 隐藏运行通过保留同一个 view/WebContents 并切换 visibility 或挂载关系实现，不复制第二套页面。
- tab 在窗口或 sidebar 间迁移时，由 main 从旧 `contentView` 移除并重新挂载到目标窗口；view generation 阻止旧布局消息控制新 owner。
- Electron main 集中处理导航、权限、下载、弹窗、输入注入和 CDP。
- agent 与用户通过显式状态机交接；用户可立即抢占。
- 高层 locator/CUA/snapshot API 默认开放；raw/full CDP 只在 Developer mode。
- 截图和下载作为有大小、来源和生命周期的受控 artifact 进入 thread/UI。
- renderer 崩溃不销毁 main-owned Browser view；页面 WebContents 崩溃只重建受影响 tab，保留 profile，并使旧 view generation 失效。
- React sidebar、modal、菜单和 tooltip 与 native view 的 bounds、z-order、遮挡和焦点策略必须通过 Windows 实机验证。

完整实施合同见 [10](10-Electron迁移与内置浏览器实现计划.md) 和 [spec 013](../.specs/013-codex-app-capability-parity/)。

## ⑥ Model Gateway

Gateway 只在目标模型不直接满足 codex Responses 合同时启用。它是独立 sidecar，负责协议翻译、流式事件、工具调用与错误映射；不拥有 thread、账号业务、Browser 或 UI 状态。

Gateway 不能成为第二 agent runtime，也不能改变 codex 的执行循环。

## 配置与凭据

- App 只写应用数据目录内的专属 `CODEX_HOME/config.toml`。
- 不读取或覆盖用户 `~/.codex`。
- provider secret 进入系统凭据存储。
- Browser Cookie 留在 App 专属 partition，不进入 thread、日志或模型上下文。
- main/daemon 目标使用子进程 stdio；Browser backend、CDP 和本地 RPC 不暴露到网络。
- 若迁移切片临时复用 loopback，必须使用动态端口、随机 capability token 和明确删除任务。

## 已暂停的层

工作台包、Session Orchestrator、插件市场、专家市场和 OPC 不属于当前运行时主链。相关目录和 specs 保留为冻结资产；P0 实现不得为它们新增并行 thread、surface 或配置写入路径。
