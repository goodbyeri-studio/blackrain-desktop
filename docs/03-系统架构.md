# 03 系统架构

> 本文描述 BlackRain 自建的平台分层。双引擎进程拓扑以 [09](09-运行时架构与里程碑.md) 为真源；产品术语以 [04](04-产品形态.md) 为真源；工作台包协议以 [.specs/008](../.specs/008-expert-workbench-package/) 为执行真源。

## 三项目边界

BlackRain 是桌面端 SaaS，但不把所有代码和服务塞进一个仓库。目标平台由三个独立项目组成，执行真源见 [.specs/010](../.specs/010-three-project-platform/)：

| 项目 | 形态 | 核心职责 |
|---|---|---|
| `blackrain-desktop` | 私有 Windows 客户端 | 工作台、项目、双引擎、本地 Core、系统凭据和云端 API client |
| `blackrain-cloud` | 私有模块化单体 SaaS | Supabase 身份、套餐、支付、商业 credit ledger、市场、broker 和 Relay 对账 |
| `blackrain-relay` | 公开 AGPL 模型中转产品 | New API、渠道、路由、model token、usage、限流、批发结算和第三方开放 API |

Cloud 是 Relay 的企业客户；两者独立数据库、密钥域和发布周期，只通过版本化 API/Webhook 交互。三个仓库是产品与信任边界，不代表小团队要立刻把 Cloud/Relay 拆成大量微服务。

## 总体架构

```text
⑦ 专家市场层（post-MVP）
   发现、授权、购买、更新、分成、评价、审核
                         ↑
⑥ 工作室编排层（post-MVP）
   多工作台目标、分工、交接、共享记忆、预算、审批、验收
                         ↑
⑤ 工作台产品层
   专家环境 = Skills + 插件 + 环境 + 资源 + 验证 + 任务入口
                         ↑
④ 工作台运行层
   Manifest、依赖解析、安装、激活、升级、回滚、卸载、健康检查
                         ↑
③ 安全与验证层
   权限、审批、备份、恢复、来源、断言、dry-run、diff、领域评测
                         ↑
② BlackRain Core
   App 监工、项目/任务、模型、配置、进程、事件、凭据、更新
                         ↑
① Agent 与工具底座
   Hermes / codex 黑盒 + Gateway + MCP / CLI / API / 本地工具
```

## ① Agent 与工具底座

BlackRain 不自研 Agent 循环：

- WORK 默认复用 Hermes，面向非开发者和工作台体验。
- CODE 复用 codex，保留专业开发者所需的原生控制力。
- CODE 通过独立 Gateway 完成 Responses⇄Chat 翻译。
- 插件通过 MCP、CLI、API、本地程序或宿主软件适配器打开“机器门”。

两个引擎都是可替换执行器。垂类资产不得写死在引擎 fork 里。

## ② BlackRain Core

Core 是所有工作台共享的系统能力：

- Windows 桌面安装和更新
- App 托管引擎与 sidecar 进程
- 专属 `CODEX_HOME` / `HERMES_HOME`
- 模型、账号、credit 和凭据
- 工作目录、项目和任务
- UI、事件、审批和成果展示
- 工作台安装、激活、停用和版本状态
- 运行日志、诊断和错误恢复

双引擎是 Core 的实现细节。用户入口优先围绕工作台和项目组织，而不是围绕 Hermes/codex 术语组织。

## ③ 安全与验证层

这里包含两条独立的信任轴。

### 安全：Agent 会不会害我

- 最小权限和授权目录
- 高危动作审批
- 安装前权限声明
- 修改前备份
- 删除进回收站
- 一键恢复
- 凭据不落明文
- 软件和脚本来源可追溯

### 正确性：结果到底对不对

- 文件数、行数和金额核对
- schema、格式和范围检查
- dry-run 和 diff
- 自检断言
- 异常项单列
- 输入到输出的来源定位
- 标准任务评测
- 人工抽检和强制确认

不同垂类的验证力度不同，但每个可发布工作台都必须至少声明自己的验证能力和未覆盖风险。

## ④ 工作台运行层

这是新定位下最重要的自建层。

工作台不能依赖作者电脑的偶然状态。运行层必须逐步支持：

- 读取工作台 Manifest
- 检查操作系统、架构、磁盘和宿主软件
- 安装或定位合法可分发的工具和运行时
- 引导用户提供账号、密钥或商业软件 License
- 创建项目目录和默认模板
- 注册 Skills、插件、MCP 和任务入口
- 执行安装后健康检查
- 记录文件、版本和权限
- 原子升级、失败回滚和完整卸载

目标协议见 [.specs/008](../.specs/008-expert-workbench-package/)。当前仓库尚未实现完整运行层。

## ⑤ 工作台产品层

工作台是一位专家数字工作环境的可复现封装：

```text
workbench
├── manifest
├── skills
├── plugins
├── environment
├── templates / examples
├── tasks
├── validation
└── docs / license / provenance
```

工作台的价值不在文件数量，而在它是否：

- 解决一个清晰岗位或领域的问题
- 安装后不需要用户重新搭环境
- 有足够好的默认任务和项目结构
- 能在真实数据上稳定交付
- 能解释权限、数据流和失败边界
- 能持续升级而不破坏用户项目

Office 是第一套参考工作台；其他垂类按市场验证逐个进入。

## ⑥ 工作室编排层

工作室不是工作台收藏夹，而是多岗位业务运行层。

只有具备以下新增能力时，才构成独立产品层：

- 共同业务目标
- 多工作台或多角色分工
- 任务派发与上下游交接
- 共享文件、记忆和状态
- 预算、权限和资源隔离
- 人工审批和最终验收
- 定时任务、运行看板和审计

工作室属于 post-MVP。单工作台尚未形成稳定闭环前，不建设复杂 OPC 编排。

## ⑦ 专家市场层

市场分发的核心商品是工作台，插件是可复用零件，Skill 是方法资产。

市场需要处理：

- 作者身份与专业证明
- 包签名、来源和版本
- License 与数据源授权
- 安全扫描和人工审核
- 兼容性、评分和退款
- 更新、弃用和迁移
- 分成、结算和防抄袭

MVP 只发官方工作台，不开放任意第三方包安装。

## 核心实体

| 实体 | 含义 | 是否可分发商品 |
|---|---|---|
| Skill | 方法和操作规程 | 可以，但容易复制 |
| 插件 | 工具和系统适配器 | 可以，偏基础能力 |
| 工作台 | 完整专家环境 | **核心商品** |
| 工作室 | 多岗位业务系统 | 高价值产品 |
| 项目 | 用户持续工作的本地空间 | 否，是运行实例 |
| 任务 | 一次具体目标 | 否，是运行实例 |
| 角色/Agent | 执行身份和权限 | 通常随工作台/工作室声明 |

## 复用与自建边界

| 能力 | 策略 |
|---|---|
| Agent 循环、工具调用、基础审批 | 复用 Hermes / codex |
| Responses⇄Chat 翻译 | 自建可替换 Gateway sidecar |
| 桌面壳、项目和任务 UI | 基于现有 Tauri 壳持续改造 |
| 工作台 Manifest 与生命周期 | **BlackRain 核心自建** |
| 垂类 Skills、插件、模板和验证 | 官方 + 专家供给，形成核心资产 |
| 模型 | 接国产模型，不自研基础模型 |
| 专家市场和分成 | post-MVP 自建 |

## 当前实现水位

- ① Agent 与工具底座：CODE 主链和独立 WORK spike 有证据，但 Windows 产品闭环未完成。
- ② Core：桌面壳、配置、Gateway 管理等大量能力存在；仍缺完整 WORK surface。
- ③ 安全与验证：有审批、diff 等上游能力和设计，工作台级备份/恢复/领域评测未形成统一协议。
- ④ 工作台运行层：尚处 spec 阶段，只有 Office 资源注入骨架。
- ⑤ 工作台产品层：Office 骨架存在，5×10 质量基线未跑。
- ⑥ 工作室、⑦市场：均为 post-MVP 蓝图。
