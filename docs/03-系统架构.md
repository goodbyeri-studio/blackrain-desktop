# 03 系统架构

## 六层架构总览

```
┌─────────────────────────────────────────────────────────┐
│  ⑥ 市场层    工作台市场 / 插件市场(人人可上传、可赚钱)      │ ← 护城河C:创作者经济
├─────────────────────────────────────────────────────────┤
│  ⑤ 体验层    「工作台」(给小白) + 自由对话(给进阶)          │ ← 护城河A:把 Codex 翻译成人话
│             带护栏的发挥 · 一键起步 · 成果可视化              │
├─────────────────────────────────────────────────────────┤
│  ④ 验证层    给非专家证明「输出是对的」(非仅「看着对」)      │ ← 护城河D:可验证
│             按垂类伸缩:可视化+抽检 / dry-run+diff / 自检断言 │
├─────────────────────────────────────────────────────────┤
│  ③ 能力封装层  工作台 = AGENTS.md + skills + MCP + 模板      │ ← 几乎零代码,纯 Markdown
│              插件 = skill / MCP server / connector          │
├─────────────────────────────────────────────────────────┤
│  ② 模型路由层  按任务分流国产模型(编排/写作/视觉/兜底)       │ ← 不锁模型,OpenAI 兼容
├─────────────────────────────────────────────────────────┤
│  ① 内核层    Codex fork:agent循环·工具·沙箱·审批·记忆·子agent │ ← 护城河B:真能干活+铁桶沙箱
└─────────────────────────────────────────────────────────┘
```

设计原则:**越底层越复用上游、越少改;越上层越是我们自己的产品和护城河。**

> **为什么是六层、验证层为什么独立**:早先(五层)把「正确性」摊在体验层的「成果可视化」里——但**可视化 ≠ 可验证**:把对账表渲染得漂亮,不等于证明里面数字对。内核层的沙箱/审批解决的是「agent 会不会害我」(安全),不解决「结果对不对」(正确性)。给一个看不懂代码、也判断不了领域内容的人**证明输出是对的**,是一件独立的产品工程,必须有自己的一层。详见 ④验证层 与 [07 护城河](07-护城河与风险.md) 护城河 D。

---

## ① 内核层 —— 复用 Codex,这是地基

Fork [openai/codex](https://github.com/openai/codex) 的 `codex-rs`(Apache-2.0)。它已具备一套完整的「安全地在真实电脑上干活」的能力,我们**几乎全盘复用,不重写**:

- **agent 循环 + 上下文压缩**:支撑长任务(压缩历史而非丢弃)。
- **文件读写 / 命令执行**:在沙箱内改文件、跑构建/脚本。
- **三档沙箱**:`read-only` / `workspace-write`(默认,仅写工作区、默认断网)/ `danger-full-access`。OS 级强制:macOS Seatbelt、Linux bwrap+seccomp、Windows 原生沙箱。
- **四档审批**:`on-request` / `untrusted` / `never` / `granular`;可把审批路由给一个 reviewer agent 自动判,高危一律拒、失败默认拒(fail closed)。
- **域名级网络策略**:allowlist/denylist,deny 优先。
- **记忆 / 子 agent / MCP 客户端**:跨会话记忆、多 agent 分解协作、连接外部工具。

> **为什么这层是护城河 B**:这整套体系是 Coze/Dify 那类「API 编排平台」给不了的。它们的 agent 跑在玩具沙箱里调 API;Codex 内核能在用户的真实电脑上安全地动手。这是「真能干活」的根基。

### 集成方式:子进程 + 协议(而非库嵌入)

桌面外壳通过 Codex 的 `app-server-protocol`(JSON-RPC)以**子进程**方式驱动内核,而不是把 `codex-core` 当库静态链接。

这句话容易被误解,这里先把边界讲死:

- **运行时不是单体单进程软件**。内核继续作为独立子进程存在,网关也保持独立进程。
- **产品交付可以是单安装包**。是否“开箱即用”取决于制品怎么打包,不取决于运行时是不是多进程。
- 我们追求的是：**用户视角的一包即用**,而不是工程视角的“把所有逻辑硬塞进一个二进制”。

| 方案 | 取舍 |
|---|---|
| **✅ 子进程 + 协议(采用)** | `app-server` 本就是为外部前端设计的稳定集成面;上游日更时 rebase 几乎不痛;进程隔离,内核崩溃不拖垮外壳,沙箱边界天然完整 |
| ❌ 库嵌入 | 集成更紧,但 `codex-core` 内部 API 不稳定、日更乱变,每次 rebase 都可能编译崩;core 里一个 panic 直接搞崩整个 app |

因为我们要做的是「忠于上游的镜像/Fork」,而上游日更,所以贴近上游的可维护性是决定性的。

## ② 模型路由层 —— 不锁模型

把所有国产模型统一抽象成 **OpenAI 兼容客户端**(换 `base_url + model + key` 即可切换),按任务自动路由到最合适的模型。详细选型见 [05 模型路由](05-模型路由.md)。

要点:
- 内核默认走 OpenAI 的 Responses 协议;国产模型是 Chat Completions。⚠️**`wire_api = "chat"` 直连这条捷径已被上游删除**(2026-06 实测,见 [codex#7782](https://github.com/openai/codex/discussions/7782) 及 [09 运行时架构](09-运行时架构与里程碑.md)),因此自带 Responses↔Chat 转译网关**从 M1 起就是硬依赖,不是可选的后期演进**。详细见 [05 模型路由](05-模型路由.md)、[09 运行时架构](09-运行时架构与里程碑.md)。
- 主控 agent(编排)与兜底/批量分离;视觉、生图、生视频走专用产品 API。

## ③ 能力封装层 —— 低代码封装的技术真相

**这是整个架构最关键的好消息**:两个引擎的扩展机制天然适合「低代码封装」。

- **Skills = 纯 Markdown + frontmatter,零编译**。一个技能 = 一个目录 + 一份 `SKILL.md`(写明 name、description、做什么),可选附 `scripts/`、`assets/`。codex 与 Hermes 都用 agentskills.io 同标准,**skill 是双引擎唯一干净共享的货币**。
- **AGENTS.md = 纯文本指令**,定义 agent 的人设、规矩、上下文。
- **MCP / connectors** 接外部数据与工具;**hooks** 做生命周期护栏(拦截、注入上下文、改写工具入参)。

含义:**懂业务的人(网文编辑、会计)写几个 Markdown 就能造一个工作台,不需要程序员**(v1 先官方造,创作者自造留后期)。

> **产品形态(技能/插件/工作台/工作室四词的定义、边界、v1 状态)是 [04 产品形态](04-产品形态.md) 的职责,本文不重复。**
> **插件目录的供给侧切分(按引擎/格式适配器打包、~34 单元、`[铺]`/`[控]`、license)是 [.specs/004-plugin-catalog](../.specs/004-plugin-catalog/) 的职责,且标注为「终局参考,非 v1 范围」——v1 只落所选垂类需要的 3-5 个。**

## ④ 验证层 —— 给非专家证明「输出是对的」(护城河 D)

「让 agent 操作电脑」会变成基础设施,「成果可视化」只解决「看得懂」;但**可视化 ≠ 可验证**——把对账表渲染得漂亮,不证明里面数字对。给一个看不懂代码、也判断不了领域内容的人**证明输出正确**,是独立的产品工程,单独成层。

**它是横切能力,不是闸门**:不决定哪个插件存在(那是「先广撒网」的事),只决定每个工作台**交付时怎么自证对错**,且力度随垂类验证成本伸缩:

| 验证成本档 | 垂类 | 脚手架力度 |
|---|---|---|
| 低 | 网文/媒体/图像/文件 | 成果可视化 + 抽检 |
| 中 | 数据报表/CAD 几何/PDF 提取 | dry-run 预览 + diff 报告 + 抽样比对 |
| 高 | 财务/XBRL/数据汇总 | 引擎自检断言(账平/借贷相等/schema)+ 强制人工确认节点 |

与内核层的区别:**内核沙箱/审批 = 「agent 会不会害我」(安全);验证层 = 「结果对不对」(正确性)。** 两者正交。沉淀出的「验证过的执行程序 + 各垂类验证脚手架」是别人复制不了的私有资产,见 [07 护城河](07-护城河与风险.md) 护城河 D。

---

## ⑤ 体验层 —— 把 Codex 翻译成人话(护城河 A)

桌面 GUI(技术选型:Tauri = Rust 后端 + Web 前端,后端可与内核子进程同栈)。把终端黑框转换成普通人能用的界面:

- **工作台 = 布置好的房间**:不是白纸,而是按钮化的任务入口(「① 起爆款名 ② 看热榜 ③ 规划大纲」)。
- **带护栏的发挥**:AI 自动铺 90% 的路,只在关键岔路口给**选项**,而不是要用户写 prompt。这是小白能用 vs 用不了的生死线。
- **成果可视化**:给用户看封面、对账表、剪好的视频,而不是命令行。
- **进阶用户**保留自由对话 + 直接调插件。

## ⑥ 市场层 —— 创作者经济(护城河 C)

工作台/插件的注册表,人人可上传、可赚钱。结构上类似 Coze Studio,但唯一且致命的区别:**这里编排的是「真能在本地动手干活的 agent」,而非 API 调用。** 设计准则(分成、分发、防抄、冷启动)详见 [06 市场与创作者经济](06-市场与创作者经济.md)。

## 自建 vs 复用:一张总表

| 能力 | 来源 |
|---|---|
| agent 循环、文件/命令、沙箱、审批、记忆、子 agent、MCP | 复用 Codex |
| 国产模型路由、Responses↔Chat 转译代理 | 自建(基于 Codex 的 provider 机制) |
| 工作台/插件的封装规范 | 自建(基于 Codex 的 skills/AGENTS.md) |
| 桌面 GUI、工作台界面、带护栏的发挥 | 自建(全新) |
| **验证层(给非专家证明输出对)** | **自建护城河 D**:按垂类伸缩的验证脚手架(可视化/dry-run+diff/自检断言),沉淀「验证过的执行程序」为私有资产 |
| 插件目录(~34 单元,按引擎切) | 自建(基于 Codex/Hermes 的 skill/MCP/ACP),见 [.specs/004](../.specs/004-plugin-catalog/) |
| 工作台/插件市场、分成、分发 | 自建(全新) |
| **「素材下载/生成」** | **自建关键缺口**:Codex 无一等公民素材工具,需用 MCP/skill 补齐(联网搜图、生图生视频) |
| 关停遥测、本地优先、审计 | 自建(改造 Codex 的 analytics/otel,做到可证明零外联) |

## 引擎策略:双引擎(working/coding)+ 四层能力 + 三档模式

2026-06 选型确定:不止 codex 一个引擎。codex 当 **coding 引擎**(强编码,完全 codex app 一致,造插件/复刻环境),引入 Hermes Agent(MIT)当 **working 引擎**(通用任务/记忆/skills,接国产 Chat 模型零翻译)。两引擎躲在协议接缝后(coding 走 app-server JSON-RPC,working 走 HTTP `/v1`),由监工壳(Tauri)编排。GUI 继续用 CodexMonitor/Tauri 壳(保住更难的 codex 接缝),只借 Hermes Desktop 的 MIT React 组件。

**产品形态的完整定义(双入口 + 技能/插件/工作台/工作室四词 + 各自 v1 状态)是 [04 产品形态](04-产品形态.md) 的职责,本文不重复。** 这里只记与架构相关的两点:

- **本地交付环境、推理走云**:工作台/工作室本地下载 + 热拔插(**云端托管工作台方案已推翻**);但模型推理(LLM / 生图 / 生视频)走云 API——本地装不下生成模型权重,且用云模型本就无法做到推理级本地隐私。口径 = 「本地 = 你的数据 + 编排 + 文件;推理走你选的云模型」。唯一服务器件是 new-api 中转(计量/差价闭环)。
- **WORK 专属**:工作台/工作室只活在 WORK 入口;CODE 入口照抄 codex app,无此概念。

完整需求/设计/决策/验证见 [.specs/003-dual-engine-architecture](../.specs/003-dual-engine-architecture/);产品形态术语见 [04 产品形态](04-产品形态.md)。

## 交付层面的结论

如果只看运行时拓扑,本项目会像很多 agent 桌面端一样,内部存在多个长期进程;但如果看用户体验,我们的目标必须是普通桌面软件的交付标准:

- 安装包自带钉死版本的 `codex` 内核。
- 安装包自带模型网关及其所需运行时。
- 安装包自带默认 plugins / skills / 模板。
- App 首次启动自动准备专属 `CODEX_HOME`,不污染用户原有环境。

因此,“不是单体单进程”与“不能开箱即用”是两回事。对本项目而言,**多进程运行是架构选择,单安装包交付是产品要求。**
