# 07 护城河与风险

## 先说结论

Agent 引擎、国产模型、桌面执行、Skills/MCP 和多 Agent 都会逐渐基础设施化。BlackRain 不能依靠“功能比大厂多”建立护城河。

真正可积累的资产是：

> 专家工作环境库存 + 环境复现能力 + 垂类验证体系 + 真实任务数据 + 专家供给网络。

## 护城河 A：工作台包与环境复现

把作者电脑上的环境搬到另一台 Windows 电脑并稳定运行，远比复制 Prompt 困难。

长期能力包括：

- 依赖和版本声明
- 运行时与工具安装
- 商业宿主软件探测
- 权限和数据流解释
- 凭据配置
- 安装后健康检查
- 原子升级和回滚
- 用户项目与工作台版本隔离
- 完整卸载和残留治理

这会形成 BlackRain 自己的工作台包协议和兼容数据库。

## 护城河 B：专家数字环境库存

真正的供给不是“会写 Prompt 的人”，而是已经拥有成熟工具链、方法和检查习惯的领域高手。

每套长期维护的工作台都沉淀：

- 工具筛选
- 专业目录和模板
- 任务顺序
- 异常处理
- 领域默认值
- 失败案例
- 更新服务

高质量工作台越多，BlackRain 覆盖的长尾市场越广。

## 护城河 C：垂类验证和真实任务数据

通用 Agent 容易演示“做了一次”，难以证明“长期可靠”。

BlackRain 应为每套工作台积累：

- 标准任务集
- 安装兼容矩阵
- 输出断言
- 领域错误分类
- 模型成功率
- 不同工具版本的回归结果
- 用户真实失败和修复

这些数据会把工作台从 Prompt 配方逐步硬化为可验证的专业执行环境。

## 护城河 D：专家与封装者网络

领域专家提供方法，封装者把方法转成可安装产品，用户真实任务反过来改进工作台。

如果平台能让专家持续获得收入，并让封装者有明确职业价值，就会形成大厂难以靠一次功能发布复制的供给网络。

## 辅助优势：引擎和模型中立

BlackRain 不自研基础模型，也不硬 fork Agent 循环，可以持续吸收上游能力，并按工作台任务选择国产模型。

这是成本和迭代优势，但不是单独成立的护城河。竞品也可以支持多模型和 Skills。

## 风险 1：定位再次滑回通用 Agent

最危险的失败方式是为了显得功能丰富，不断增加通用办公入口，最终变成 WorkBuddy、Kimi Work、QoderWork 的弱小复制品。

应对：

- 首页和路线图以工作台为单位
- 每套工作台必须有清晰岗位和标准任务
- 通用 Core 能力不直接等于市场卖点
- Office 只作为参考实现，不吞掉全部产品身份

## 风险 2：工作台只是 Prompt 文件夹

如果工作台没有可复现环境、安装协议、验证和维护，它就只是模板市场，很容易被复制，也无法兑现“获得高手电脑”。

应对：推进 [.specs/008](../.specs/008-expert-workbench-package/)，把 Manifest、依赖、权限、安装、升级、验证和卸载做成一等能力。

## 风险 3：专家电脑不可合法复制

高手电脑里可能包含：

- 商业软件
- 不允许再分发的数据
- 私有脚本和客户资料
- 个人账号、Cookie 和密钥
- GPL/AGPL/BSL 或无许可证代码
- 只能在特定组织网络使用的系统

应对：

- 工作台只声明依赖，不复制无权分发的制品
- 商业软件采用“检测用户已安装并引导授权”
- 凭据由用户本地配置
- 包内文件记录来源和 License
- 对数据连接和出境路径做显式说明
- 市场上架做自动扫描和人工审核

## 风险 4：环境复现比预想更难

Windows 版本、CPU 架构、PATH、驱动、区域设置、Office 版本和安全软件都会导致“作者电脑能跑、用户电脑不能跑”。

应对：

- 首发只支持 Windows x64 的明确版本矩阵
- 依赖尽可能随包或使用可复现安装源
- 安装前 doctor，安装后 smoke
- 工作台声明兼容矩阵
- 失败时可回滚且不破坏用户电脑
- 从 Office 参考工作台积累兼容经验

## 风险 5：复制工具不等于复制判断力

小白获得专家工具和方法后，仍可能无法处理边界情况。对外宣传“安装即成为专家”会带来信任和责任风险。

应对：

- 承诺专业工具、环境和工作方式，不承诺专家身份
- 不确定结果显式标注
- 高责任结论要求人工确认
- 工作台写清适用范围和非目标
- 让专家评测成为发布和更新的一部分

## 风险 6：金融、医疗、法律等高责任领域

股票研究工作台可以提供数据获取、研究框架、回测和风险分析，但不能在缺乏合规设计时宣传自动荐股或收益保证。

医疗、法律、财税等同理。工具执行、信息整理和专业判断必须分层，必要时限制自动化动作。

## 风险 7：安全与恢复不足

当前 Windows MVP 尚不能宣传为 OS 级强沙箱。WORK/Hermes 主要依赖应用层审批，codex 的 Windows 沙箱能力也必须以实机验证为准。

工作台安装和执行会扩大风险面，因此必须逐步补齐：

- 授权目录
- 安装权限预览
- 脚本来源和签名
- 修改前备份
- 删除进回收站
- 一键恢复
- 网络和凭据审计

第一起“工作台把电脑搞坏”的公开事故可能摧毁整个品类信任。

## 风险 8：市场冷启动

没有专家就没有优质工作台，没有用户就没有专家收入。

应对不是先开放上传，而是和少量真实专家联合打磨少量高质量工作台，证明陌生用户愿意安装、复用和付费。

## 风险 9：分发和获客

工作台具有天然可演示性，但当前仍缺明确的第一批用户和渠道。

每套候选工作台在正式开发前都应先用真实场景 demo 验证：

- 用户是否一眼理解价值
- 是否愿意交出真实文件或连接真实环境
- 是否重复使用
- 是否愿意付费
- 失败时是否仍信任产品

## 数据与隐私边界

本地工作台不等于全程离线。使用云模型时，推理内容会发送到用户选择的模型链路。

可以承诺的内容必须来自真实审计，例如：

- BlackRain 自身不训练用户内容
- 平台不保留任务正文
- MeiMei API 只记录必要的请求计量与运营元数据，不默认保留任务正文

在服务端和日志审计完成前，不得提前宣传“不留存”或“数据绝不出本地”。

## 黑马判据

BlackRain 是否成为黑马，不看功能清单，而看：

1. 是否能把一位真实高手的电脑环境复现在陌生用户电脑上。
2. 是否能让小白在明确任务上稳定获得专业交付物。
3. 是否形成一个大厂通用 Agent 做不深的垂类心智。
4. 是否能把第一套工作台的方法复制到第二、第三个长尾领域。
5. 是否让专家从工作台获得持续收入。

只有这五件事成立，工作台平台才不是概念。
