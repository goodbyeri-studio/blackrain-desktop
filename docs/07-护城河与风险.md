# 07 护城河与风险

> 诚实地把「能赢在哪」和「可能死在哪」摆清楚。蓝图的价值不在于乐观,而在于看清真问题。

## 四处护城河

「让 agent 能操作电脑」本身**不会**是护城河——字节 Coze 已在做(见 [02 市场与竞品](02-市场与竞品.md)),它会变成基础设施。同理,「能调用某个软件的机器门」也不是护城河(人人都能写脚本调 API)。我们能守住的,只有字节**商业模式或战略重心决定的盲区**,以及一件别人没做好的硬活:**向非专家证明输出是对的**。

### 护城河 A:把 Codex 翻译成人话(体验)
让非开发者丝滑地用上 Codex 全部能力,核心是「工作台 + 带护栏的发挥」。这是产品手艺活,不是单点技术,难被快速复制。详见 [04 产品形态](04-产品形态.md)。

### 护城河 B:不锁模型(商业模式)
Coze(coze.cn)必然主推豆包,因为字节要卖自己的模型和云。2049 没有模型要卖,可以中立地把全网国产模型摆上货架让用户自己挑(按任务自动选的 Auto-Mode 是大后期方向)。**这是字节商业模式上的死穴,它学不来。**

### 护城河 C:真给创作者分钱(战略重心)
字节做生态是为了流量和模型调用,「让创作者赚到钱」不是它的优先级(其付费插件分成比例至今不公开)。2049 把创作者经济当头等大事,这是飞轮的燃料,也是差异化。

### 护城河 D:给非专家证明「输出是对的」(可验证)
**可视化 ≠ 可验证。** 把对账表渲染得漂亮(可视化)只解决「看得懂」;证明里面第 4000 行数字没算错(可验证)才解决「信得过」。给一个看不懂代码、也判断不了领域内容的人**证明输出正确**,是没人做好的硬活——执行 AI 已经够用,「制造可信」才是真壁垒。

这条护城河沉淀的私有资产 = **「验证过的执行程序 + 各垂类验证脚手架」**:每个领域、每个客户跑过的真实任务,沉淀成带自检的确定性程序(而非每次临场推导的提示词)、校验规则、异常处理库。别人有模型、有插件目录也复制不了这套语料和脚手架。它在架构上单独成 ④验证层(见 [03 系统架构](03-系统架构.md)),按垂类伸缩力度(低=可视化+抽检;中=dry-run+diff;高=自检断言+强制确认)。

> **与「先广撒网」不冲突**:广撒网决定「造哪些插件、什么顺序」(reach-first,不按验证成本过滤);验证层决定「造出来怎么交付才让人信」(横切能力,不是闸门)。两者分属两层,见 [.specs/004 decisions](../.specs/004-plugin-catalog/decisions.md)。

> **附加层:垂直深度 + 本地优先。** 字节做大而全的「数字社会」;我们聚焦把少数垂类做到惊艳,且数据本地优先——对网文写手(怕创意泄露)、代账会计(怕账目外流)是强卖点,且与字节的云生态战略天然冲突。

## 三大硬风险

### 风险 1:与字节的窗口期 —— 这是计时器
Coze 2.5/3.0 已在做「agent 配云设备、后台干活、拉 Codex 进协作」。我们的「操作电脑」差异点正在被追平。

**应对**:不与字节比「谁的 agent 更全能」,而把全部赌注押在它结构上做不到的三处护城河(A/B/C)+ 别人没做好的验证层(D),共四处;执行速度要快;极窄切入,先在一个垂类建立不可撼动的深度和创作者生态。

### 风险 2:「让小白敢装、敢用」是最硬的一仗 —— 比技术更难
Codex 强在沙箱 + 审批,但那是给程序员的安全感。让一个网文写手或会计**安装一个本地 agent、看着它在自己电脑上执行操作而不恐慌**——这件事没有现成答案可抄,产品工作量可能比工作台本身还大。这是「面向非开发者」五个字里最重的部分。

**应对**:把安装→首次运行→信任做到无感;高危动作默认弹审批、用大白话解释「它要做什么、有什么后果」;成果可视化而非命令行;数据本地优先,从信任上正面化解恐惧。

> **两条信任轴,别混**:风险 2 的「敢用」= **「agent 会不会害我」(安全)**,靠沙箱 + 审批 + 本地优先解决;它**不**解决**「结果对不对」(正确性)**——那是护城河 D / ④验证层的事。沙箱挡住「灾难性动作」,可视化解决「看得懂」,都不证明「内容是对的」。两轴正交,各有各的解法,不能用一个冒充另一个。

### 风险 3:「造工作台」能否低代码到让业务人自己干 —— 平台规模化的命脉
技术上成立(skills 是纯 Markdown),但「写 Markdown」对程序员是零代码,对网文编辑仍是门槛。如果造工作台始终需要程序员,2049 就只是「我们自己做几个工作台的垂类工具」,而非平台。

**应对**:把「造工作台」这件事本身也做成普通人能干的(可视化造台、AI 辅助生成 skill、从对话沉淀成工作台)。这是最后一道、也最难的产品设计题,决定天花板。

## 其他需警惕的坑

- **创作者市场全行业无成功先例**:GPT Store 是反面教材。分成必须 day-1 真落地、分发即产品、防抄前置、瞄准真付费人群。详见 [06 市场与创作者经济](06-市场与创作者经济.md)。
- **定价不透明劝退普通人**:Manus 的 credit 制教训。C 端用封顶订阅,给清晰用量预期。
- **「真操作电脑」= 安全/责任/成本三重雷**:误操作、越权、隐私、不可逆动作(删数据/发消息/付款)。必须沙箱隔离 + 高危人工确认 + 权限边界。既是安全要求,也是信任卖点。
- **素材能力是自建缺口**:Codex 无一等公民的素材下载/生成,需用 MCP/skill 补齐。
- **监管合规**:2026 年中国已出 AI Agent 政策框架。模型准入、数据出境、agent 自动对外发消息/交易都有合规要求。本土合规可成护城河,但也是硬门槛。

## 数据立场（2026-06-26 松绑：不强制、用户自担）

**不再强制「数据不出本地 / 不追高敏垂类」。是否碰高敏场景、云端类能力,由用户自担风险,产品不设限、不替其兜底。**

事实背景:连 codex、Hermes,只要用第三方云模型 API,都做不到推理级的绝对本地隐私——提示词/内容必须发到模型厂商才能推理,这是用云模型的物理宿命。我们的链路(用户机器 → BlackRain → new-api 中转 → 国产模型厂商)同理,推理出本地不可避免。纯本地形态下,对话模式的项目数据本就不出本地;高敏与否交给用户自选。

仍守两条**零成本底线**(与高敏无关,是任何产品的卫生标准,无论松不松绑都守):

1. **BlackRain 自己不训练、不留存用户内容** —— 能 100% 做到的信任基本盘。
2. **new-api 中转不落内容明文**(只记计量元数据:token 数/时间/模型) —— 利润发动机穿过所有用户推理流量,一旦存内容明文就是会被拖库的集中数据池,这是安全事故风险,不是隐私承诺问题。

对外话术(诚实、零成本、够用):**「我们不碰你的数据,推理走你选的模型。」** 不夸大成「全程本地」——说实话成本为零,被发现夸大则信任崩塌。

> **「用户自担」只覆盖隐私轴,不覆盖正确性轴(增量澄清,不推翻 06-26)。** 这里有两条不同的风险轴,别用一条话术兜两件事:
> - **隐私轴**(数据出不出本地、上不上云):**用户自担成立**——是用户自己的数据、自己的选择,产品不设限、不兜底。这就是 06-26 决策的范围。
> - **正确性轴**(agent 把税算错了、对账对错了):**不能甩给用户自担**——前提恰恰是这个用户**判断不了对错**(他若能判断,就不需要这个 agent)。把「我验不出来的错误」算成「我自担的风险」是无效的,这条由产品经 **④验证层 / 护城河 D** 承担(按垂类伸缩的自检脚手架),不属于「用户自担」。

> 注:早先(2026-06-25)曾定「不追高敏垂类、受众只锚创作类」,2026-06-26 松绑为「不强制、用户自担」(仅隐私轴)。完整取舍见 [.specs/003-dual-engine-architecture/decisions.md](../.specs/003-dual-engine-architecture/decisions.md)。

## 许可证与合规义务

计划 Fork 的 [openai/codex](https://github.com/openai/codex) 为 **Apache-2.0**。商业 Fork 合法,但有义务:

- 保留原始版权声明与 `LICENSE`;
- 保留并随发行附带 `NOTICE` 文件;
- 在显著位置**声明对原作品的修改**;

合规红线:不要做成抹掉来源出处的样子。

## 一句话总结

2049 App 能不能成,不取决于「能否让 agent 操作电脑」(那会成为基础设施),而取决于四件事能否做到:**① 把它做得让普通人敢用、会用;② 守住不锁模型 + 真分钱这两条字节学不来的护城河;③ 让造工作台这件事本身也下放给普通人;④ 给非专家证明「输出是对的」(可视化≠可验证),把验证过的执行程序沉淀成私有资产。** 这四件事,每一件都难,但每一件都不是靠钱和模型就能碾过来的——这正是一个没有大厂资源的团队唯一的机会所在。
