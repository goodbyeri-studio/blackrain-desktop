# 04 产品形态

> **本文是产品形态唯一真源。** Skill、插件、工作台、工作室、项目、任务和角色的定义只在这里维护。运行时进程以 [09](09-运行时架构与里程碑.md) 为准；工作台包实现以 [.specs/008](../.specs/008-expert-workbench-package/) 为准。

## 一、产品第一主语：工作台

BlackRain 面向用户呈现的核心不是引擎，也不是空白对话框，而是可安装的专业工作台。

一个工作台代表一位领域高手已经配置好的数字工作环境：

- 他使用的工具
- 他组织项目的方式
- 他反复使用的模板和数据源
- 他解决问题的步骤
- 他检查结果和处理失败的方法

AI 是这套环境的操作者、讲解者和协作者。

## 二、价值台阶与正式关系

对用户可以使用简单台阶：

> **Skill → 插件 → 工作台 → 工作室（OPC 一人公司）**

但正式架构不是严格的单链继承：

```text
Skill + 插件 + 环境 + 资源 + 验证
                    ↓
                 工作台
                    ↓
            工作室（OPC 一人公司）
```

一句话记忆：

> Skill 复制高手的方法，插件复制高手的工具，工作台复制高手的电脑，工作室复制高手的团队。

## 三、Skill：知道怎样做

Skill 是领域方法、操作规程和判断顺序。

例如“财报质量分析 Skill”可以描述：

- 先看哪些表
- 计算哪些指标
- 哪些异常需要追问
- 如何交叉验证
- 最终报告包含什么

Skill 可以带模板、示例、资源和辅助脚本，但原则上只使用当前已授权的工具与环境；它本身不应静默扩大系统权限或引入未声明的外部服务。

## 四、插件：获得新的手

插件给 Agent 新增可执行能力，打开某个软件、数据源或系统的“机器门”。

插件可以包含或声明：

- MCP Server
- CLI / 本地可执行程序
- API Connector
- 浏览器或桌面适配器
- 宿主软件桥接
- 运行时依赖
- 权限、密钥和数据流
- 配套 Skills

Skill 与插件是平级原语：有插件没 Skill，Agent 可能不会正确使用工具；有 Skill 没插件，Agent 只能给建议而不能真正执行。

## 五、环境、资源与验证

它们不是新的营销层级，但都是工作台的一等组成部分。

### 环境

- 操作系统和架构要求
- Python / Node / Java 等运行时
- 系统包和本地工具
- 目录结构和默认配置
- 商业宿主软件及最低版本
- 环境变量、账号和凭据槽位

### 资源

- 模板
- 样例项目
- 示例数据
- 术语库
- 默认配置
- 任务入口和说明

### 验证

- 安装健康检查
- 标准任务 smoke
- 输出 schema 和格式检查
- 领域断言
- dry-run / diff
- 来源和审计信息
- 失败恢复与卸载检查

## 六、工作台：可安装的专家数字工作环境

工作台是 BlackRain 的核心商品。

它面向一个清晰领域、岗位或任务体系，而不是泛泛地声明“什么都能做”。例如：

- Office 文件批处理工作台
- A 股基本面研究工作台
- 跨境电商选品工作台
- 招投标资料工作台
- GIS 数据处理工作台
- 学术文献研究工作台

一个合格工作台至少要回答：

1. 给谁使用，解决什么任务？
2. 需要安装或连接哪些工具？
3. 需要哪些账号、数据源和 License？
4. 会访问哪些文件和网络？
5. 默认项目目录和任务入口是什么？
6. 怎样证明安装正确、结果基本可信？
7. 怎样升级、回滚和卸载？

目标目录结构见 [.specs/008](../.specs/008-expert-workbench-package/)。在该 spec 落地前，当前 `workbenches/office-agent/` 只是内容和注入骨架，不代表完整工作台包已实现。

## 七、工作室：多个数字岗位组成 OPC 一人公司

工作室不是多个工作台的收藏夹，而是一个多岗位业务系统。

它必须提供工作台之上的新增能力：

- 共同目标和业务状态
- 多岗位分工
- 任务派发和交接
- 共享文件与记忆
- 权限、预算和资源控制
- 人工审批和最终验收
- 定时运行、看板和审计

例如跨境电商工作室可以包含：市场研究、选品、内容生产、上架运营和数据复盘工作台。

工作室属于 post-MVP。单工作台模型尚未验证前，不实现复杂多 Agent 公司编排。

## 八、项目、任务和角色

这三个是运行实体，不是商品层级。

| 概念 | 定义 |
|---|---|
| 项目 Project | 用户持续工作的本地空间，保存文件、上下文、历史和结果 |
| 任务 Task | 一次具体目标，例如“分析这 20 家公司的现金流” |
| 角色 Role/Agent | 工作台或工作室中的执行身份、方法和权限 |

工作台是可以安装和复用的“环境模板”；项目是某个用户基于工作台产生的运行实例。升级工作台不得覆盖用户项目数据。

## 九、用户入口与双引擎

WORK/Hermes 和 CODE/codex 仍是当前运行时的两个 surface，但不再作为品牌第一层分类。

用户优先看到工作台：

```text
我的工作台
├── Office 办公
├── 软件开发
├── 股票研究
└── 安装更多工作台
```

- 普通工作台默认由 WORK/Hermes 承载，使用小白友好的任务入口和护栏。
- 软件开发工作台可以进入 CODE/codex 原生 surface，保留专业控制力。
- 某些未来工作台可以按能力需要选择执行引擎，但用户不应承担引擎配置复杂度。
- 两个引擎仍不在一轮活对话中直接热切；跨引擎由 Core 切分干净子任务。

## 十、带护栏的发挥

工作台不是固定表单，也不是空白聊天框。

设计原则：

1. 入口写任务，不写工具名。
2. 默认环境和模板足够好。
3. 关键岔路口给少量选项。
4. 高危操作解释后确认。
5. 用户随时可以切到自由对话。
6. 结果用预览、表格、diff 和异常清单呈现。
7. 不确定处显式标出，不伪装成确定答案。

## 十一、首批范围

- **平台**：MVP 仅 Windows。
- **参考工作台**：Office，用于验证工作台运行层和交付闭环。
- **软件开发**：保留 CODE/codex 能力，作为内置专业环境和工程资产，不打编码红海。
- **专家市场**：post-MVP；MVP 只允许官方或签名内置工作台。
- **工作室**：post-MVP。
- **第二套垂类工作台**：待真实专家访谈和场景验证后决定。

## 十二、成熟度路径

工作台不是一次写完的 Prompt，而是逐步硬化的专业环境：

```text
① 专家方法 + 现成工具，跑通一次
      ↓
② 固化目录、模板、Skills 和插件组合
      ↓
③ 声明依赖，做到可重复安装
      ↓
④ 把重复步骤变成确定性脚本
      ↓
⑤ 加入领域验证、异常处理和恢复
      ↓
⑥ 用真实任务持续更新评测与版本
```

可发布工作台的价值不在“拥有多少 Skill”，而在“普通用户能否在一台新电脑上稳定获得接近专家工作方式的结果”。

## 十三、责任边界

BlackRain 可以复制工具、环境、方法和检查流程，但不能保证复制专家多年形成的判断力。

对外应使用：

> “快速获得专家级工具、环境和工作方法，在明确任务上提升到专业交付水准。”

不得承诺：

- 安装工作台就成为领域专家
- 股票收益或自动荐股结果
- 医疗诊断正确
- 法律意见必然有效
- 未经验证的“全自动无错误”
