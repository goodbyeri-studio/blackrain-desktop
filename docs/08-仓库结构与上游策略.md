# 08 仓库结构与上游策略

> 本文解释“代码和文档放哪里、上游如何跟进”。运行时边界以 [09 运行时架构与里程碑](09-运行时架构与里程碑.md) 为唯一真源；工作台包协议以 [.specs/008](../.specs/008-expert-workbench-package/) 为执行真源；当前实现以对应 spec `verification.md` + 实际代码/配置为准。

## 三项目仓库

| 仓库 | 可见性 | 纪律 |
|---|---|---|
| `goodbyeri-studio/blackrain-desktop` | 私有 | 本仓；用户电脑上的桌面产品、工作台和本地运行时 |
| `goodbyeri-studio/blackrain-cloud` | 私有 | BlackRain SaaS 后台；模块化单体起步，不承载模型内容转发 |
| `goodbyeri-studio/blackrain-relay` | 公开 | 独立 AGPL 中转站；基于 New API，保留署名和源码义务，可服务第三方 |

三仓边界以 [.specs/010](../.specs/010-three-project-platform/) 为执行真源。Supabase 配置、migration、邮件模板和历史 credit proxy 已迁入 `blackrain-cloud`；本仓只保留账户/session 客户端、系统凭据、Cloud API 客户端接缝和 CODE 本地翻译网关，不承载 Cloud/Relay 服务端实现。

## 本仓目录布局

```text
blackrain-desktop/               ← 桌面产品 monorepo（本仓）
├── README.md                    ← 全仓入口与当前状态
├── AGENTS.md / CLAUDE.md        ← 根 agent 契约，规则同步维护
├── docs/                        ← 文档地图、01–09 专题、命令与运行手册
├── .specs/                      ← living spec：需求/设计/任务/决策/验证
├── apps/
│   └── desktop/                 ← Tauri 桌面外壳，git subtree 自 CodexMonitor
├── gateway/                     ← CODE 专用 Responses⇄Chat 翻译 sidecar
├── plugins/                     ← 工具适配器、MCP/CLI/API connector 与配套 Skills
├── workbenches/                 ← 专家工作台包；当前只有 Office 内容/注入骨架
├── scripts/                     ← 开发、发行、引用拉取脚本
│
│   —— gitignored 本地上游，不进入本仓历史 ——
├── codex-upstream/              ← CODE 引擎：openai/codex 黑盒
└── hermes-upstream/             ← WORK 引擎：NousResearch/hermes-agent 黑盒
```

## 三种代码，三种纪律

| 类型 | 位置 | 是否修改 | 更新方式 |
|---|---|---|---|
| **引擎黑盒** | `codex-upstream/`、`hermes-upstream/` | 默认只读，不改 agent 循环 | 评估新版本后显式切到钉死 commit/tag，重新构建并跑 Windows 验证矩阵 |
| **桌面底盘** | `apps/desktop/` | 日常直接改，普通 commit | CodexMonitor 用 `git subtree`；上游同步是维护者动作 |
| **BlackRain 产品层** | 工作台运行层、`gateway/`、`plugins/`、`workbenches/`、账号/计费与壳外围 | 自建并持续演进 | 普通 GitHub Flow；跨层变更同步 living spec |

核心原则：**越底层越复用上游、越少改；越上层越是 BlackRain 自己的产品。** Agent 引擎和模型可替换，工作台 Manifest、环境复现、垂类验证和专家供给才是 BlackRain 应长期拥有的资产。这不等于“跟随上游 HEAD 运行”：发行制品必须来自已评估、可复现的锁定版本。

## 工作台代码与内容边界

新定位下，`workbenches/` 不再被定义为“纯 Markdown 内容目录”。目标工作台可以包含或引用：

- Manifest 和版本元数据
- Skills、模板、样例和任务入口
- 插件依赖和工具安装声明
- 运行时、宿主软件和数据连接要求
- 安装后健康检查和领域验证
- License、来源、权限和数据流说明

但工作台包不得随意复制商业软件、私有数据、用户凭据或无权再分发的第三方代码。完整包格式、安装/升级/卸载边界和开放问题见 [.specs/008](../.specs/008-expert-workbench-package/)。

## 双引擎上游

| 上游 | 角色 | 本地路径 | 目标锁定版本 | 纪律 |
|---|---|---|---|---|
| [openai/codex](https://github.com/openai/codex) | CODE 引擎，`app-server` JSON-RPC | `codex-upstream/` | `44918ea` / rust-v0.144.1 | Apache-2.0；只读、不改循环；CODE 经本地 Gateway 接国产模型 |
| [NousResearch/hermes-agent](https://github.com/NousResearch/hermes-agent) | WORK 引擎，HTTP `/v1` | `hermes-upstream/` | `9de9c25` / v2026.7.7.2 | MIT；只读、不改循环；WORK 直接走 Chat Completions/new-api |

上述版本是**目标锁定值**。当前 `scripts/fetch-references.sh` 会拉取精确稳定 tag、校验 tag 对应的完整 SHA，并 detached checkout；脚本成功代表源码版本已对齐，但不代表二进制构建、协议探针或 Windows 产品验证通过。验证边界见 [REFERENCES](REFERENCES.md)。

## 桌面壳：CodexMonitor subtree

`apps/desktop/` 是住在仓库里的可持续改造底盘，不是只读 vendor 依赖。选择 subtree 的原因：

- 代码留在单仓内，日常可直接编辑、测试、提交。
- 仍保留按需吸收 CodexMonitor 上游更新的通道。
- 上游同步产生的冲突和回归必须由维护者集中处理，不能在普通功能 PR 中顺手拉取。

具体 subtree 命令只维护在 [commands](commands.md)；同步后必须按改动范围跑前端、Rust 和 Windows 实机验证。

## 文档与 living spec

| 位置 | 真源职责 |
|---|---|
| `README.md` | BlackRain 定位、全局当前状态、关键入口 |
| `docs/01`–`docs/03` | 愿景、市场和系统分层 |
| `docs/04-产品形态.md` | **产品形态唯一真源** |
| `docs/05`–`docs/08` | 模型、市场、风险、仓库/上游专题 |
| `docs/09-运行时架构与里程碑.md` | **运行时边界唯一真源** |
| `.specs/008-expert-workbench-package/` | **工作台包格式与生命周期执行真源** |
| `.specs/<NNN-slug>/` | 单功能的 requirements/design/tasks/decisions/verification |
| 实际代码/配置 + spec `verification.md` | 当前实现水位 |

同一事实不要在多个专题里复制。无法收敛的架构或商业问题必须在对应 `decisions.md` 标成待决，而不是让不同文档各写一套。

## 上游更新纪律

1. 先只读评估 release notes、许可证、安全修复和协议变化。
2. 决定跟进后，显式 checkout 新 commit/tag，记录旧值与新值。
3. 构建目标制品，跑协议/能力探针和 Windows MVP 验证矩阵。
4. 同步更新 `docs/REFERENCES.md`、`AGENTS.md`、`CLAUDE.md`、相关 spec `decisions.md` / `verification.md`。
5. `.scratch/` 只存本地临时证据，绝不提交；可复用结论必须整理进 spec verification。

完整例行流程见 [upstream-update-checklist](upstream-update-checklist.md)。

## 平台边界

MVP 只发行 Windows。macOS / iOS 代码只作为 post-MVP 或 CodexMonitor 上游资产保留，不进当前发布矩阵，也不能用来替代 Windows 的 NSIS、Credential Manager、真实对话、Office 与安装/卸载验证。
