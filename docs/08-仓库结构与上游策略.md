# 08 仓库结构与上游策略

## 目录布局

```
2049-app/                      ← 产品 monorepo（本仓）
├── docs/                      ← 产品文档（01-08）
├── apps/
│   └── desktop/               ← 桌面外壳，fork 自 CodexMonitor（底盘，持续魔改）
├── gateway/                   ← 模型路由 / Responses⇄Chat 翻译层
├── plugins/                   ← 能力封装：插件 / 工作台模板
├── workbenches/               ← 工作台（已存在）
├── scripts/                   ← 工具脚本
└── codex-upstream/            ← Codex 内核本地克隆（.gitignore，不入库，黑盒子进程）
```

## 核心区分：内核 = vendor 式黑盒；壳 = fork 式底盘

设计原则（架构 [03](03-系统架构.md) 第 21 行）：**越底层越复用上游、越少改；越上层越是自己的产品。** 这直接决定两个上游各自怎么待：

| | Codex 内核 | CodexMonitor 壳 |
|---|---|---|
| 角色 | spawn 的子进程，黑盒 | 住在里面的底盘 |
| 改不改 | **不改**（子进程+协议，绝不库嵌入，见 03 第 38-47 行） | **大改**（provider 面板 / 网关 / 工作台 UI 全长在里面） |
| 放哪 | `codex-upstream/`（gitignore，本地克隆） | `apps/desktop/`（fork 入库） |
| 为什么不能反过来 | 库嵌入会被上游日更的不稳定内部 API 拖垮 | Tauri app 是单一编译单元，魔改必须在它的 src 里；vendor 只读快照会丢掉 upstream 合并能力，而 03 第 47 行明说「贴近上游可维护性是决定性的」 |

**结论：CodexMonitor 不进 `vendor/`，作为 fork 放 `apps/desktop/`。** `vendor/` 的语义是只读外部依赖；壳是底盘，不是依赖。

## 已定：CodexMonitor 用 git subtree 进 `apps/desktop/`

三种机制权衡如下，最终选 **subtree**——单仓单步、直接编辑提交，最贴「先把壳搭起来持续魔改」的节奏：

| 机制 | 单仓体验 | upstream 合并 | 代价 |
|---|---|---|---|
| **✅ git subtree（采用）** | ✅ 代码就在 `apps/desktop/`，直接编辑提交 | `git subtree pull` 合并上游 | 历史混入主仓；命令略繁琐 |
| git submodule | ⚠️ 独立 fork 仓，主仓存指针 | fork 仓挂 `upstream` remote，merge 后 bump 指针 | 双仓双步工作流，日常编辑有摩擦 |
| 直接拷贝（断关系） | ✅ 最简单 | ❌ 丢失 upstream 合并能力 | 上游日更将无法廉价同步，与 03 第 47 行冲突 |

### 实际导入命令（已执行）

```bash
# 一次性导入（--squash：上游全史压成单提交，不污染主仓）
git subtree add --prefix apps/desktop \
  https://github.com/Dimillian/CodexMonitor main --squash

# 同步上游日更
git subtree pull --prefix apps/desktop \
  https://github.com/Dimillian/CodexMonitor main --squash
```

导入产生两个提交：`Squashed 'apps/desktop/' content` + `Merge commit ... as 'apps/desktop'`。日常编辑 `apps/desktop/**` 无需任何 subtree 特殊操作，正常 commit 即可。上游自带 `README.md` 保持不动，2049 侧集成约定写在 `apps/desktop/README.2049.md`。
