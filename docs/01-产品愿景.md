# 01 产品愿景

## 一句话定义

> **BlackRain 以开源 `codex-rs` 为唯一内核，自行补齐完整 Codex 桌面产品的闭源宿主能力。**

我们的目标不是发明第二套 agent，也不是把多个 agent 拼成平台。目标是把已经开源、持续演进的 Codex 内核，变成一款功能完整、体验成熟、可长期跟随上游的 Windows 桌面产品。

## 开源内核不等于完整 App

`codex-rs` 解决 agent 循环、thread、工具调用、审批、事件和 app-server 协议。用户真正使用的桌面产品还需要：

- 稳定的窗口、项目和会话界面
- 文件、终端、Git、diff 与审批体验
- in-app browser 和持久登录态
- 下载、权限、通知、更新和系统集成
- 崩溃恢复、诊断、性能与安装交付
- 对上游能力的持续盘点和产品化

BlackRain 的价值集中在这条差距上：内核跟随上游，宿主能力由我们补齐。

## 产品原则

1. **一个内核**：只使用原装 `codex-rs` / `codex app-server`，不引入任何第二 agent runtime。
2. **行为对齐**：以官方 Codex App 的用户可感知能力和体验为标杆。
3. **合法自研**：不复制、反编译或分发闭源代码和专有资源。
4. **上游友好**：尽量通过公开协议和薄适配接入，不把产品资产写进内核 fork。
5. **证据优先**：协议存在、包装存在、UI 存在、E2E 通过和发布可用分别记录。
6. **Windows 交付**：MVP 的最终判断来自 Windows 实机制品，不来自概念图或 macOS smoke。

## 当前两个 P0

### P0-A：补齐 Codex App 能力

建立版本化能力矩阵，逐项回答：

- 当前锁定 `codex-rs` 已经提供什么？
- 官方桌面产品还有哪些宿主行为？
- 差距属于 Electron main/preload、React UI、原装 app-server 还是 Gateway？
- 什么证据才允许标记为已补齐？

第一项能力是 in-app browser。它必须让 agent 和用户围绕同一可见页面协作，而不是简单打开系统浏览器。

### P0-B：交付 Windows Electron

当前代码已完成 Electron native-clean 迁移。Electron main 按 Codex App 架构直接启动原装 `codex app-server`，通过 stdio JSONL 管理协议与生命周期，React UI 位于 renderer；当前 P0 是正式签名和 Windows 产品矩阵。

Browser 与 Desktop 通过同一个纵向切片相互验证：Electron main 启动 bundled `codex.exe app-server`，运行 Codex thread，并控制一个持久、隔离、可接管的 Browser view。

## 用户

BlackRain 首先服务需要桌面级 Codex 工作流、又希望获得更开放宿主能力的开发者和高强度电脑工作者。他们关心的是任务能否在一个统一 App 中完成、观察、接管和恢复，而不是底层用了多少套 agent。

## 暂停范围

以下方向保留已有资产，但不进入当前 P0/P1：

- 专家工作台包与 Session Orchestrator
- Office 参考工作台
- 插件市场和专家市场
- OPC/工作室、多岗位和多 Agent 公司编排

重新启动这些方向必须基于 Codex-first 桌面产品已经形成可靠闭环，并重新做产品与架构决策；旧文档不能自动恢复为路线图。

## 成功判据

BlackRain 第一阶段成功，不看工作台数量或平台故事，而看：

1. 原装 `codex-rs` 能否在 Electron Windows 制品中稳定运行。
2. 核心 Codex 工作流是否达到完整桌面产品水位。
3. in-app browser 是否能被 agent 操作、被用户观察与接管，并安全恢复。
4. 上游升级是否可以用能力矩阵和自动化验证快速吸收。
5. 产品是否建立自己的实现、品牌和交付质量，而非停留在 CodexMonitor 换皮。
