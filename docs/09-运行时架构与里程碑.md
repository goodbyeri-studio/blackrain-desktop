# 09 运行时架构与里程碑

> **本文是 Desktop 运行时边界的唯一真源。** [03 系统架构](03-系统架构.md) 讲平台分层，[04](04-产品形态.md) 定义工作台产品，[.specs/008](../.specs/008-expert-workbench-package/) 定义目标工作台包协议，[.specs/009](../.specs/009-hermes-work-surface/) 定义 Hermes WORK surface 实施闭环，[.specs/010](../.specs/010-three-project-platform/) 定义 Desktop/Cloud/Relay 的跨项目边界；本文只讲“Desktop 跑起来时有几个进程、谁管谁、工作台怎样选择执行器”。当前完成度仍以对应 spec `verification.md` + 实际代码/配置为准。
> 当前规范产品名为 **BlackRain**；`2049 App` / `2049` 是历史旧称。MVP 仅发行 Windows，macOS / iOS 属于 post-MVP 或上游资产。

## 一句话

桌面 App 是工作台运行监工：它管理工作台激活状态、权限和项目，并看管两个原装黑盒执行引擎——普通工作台默认走 Hermes，软件开发工作台进入 codex；CODE 的 Responses⇄Chat 翻译锁在模型网关进程里，WORK 直接走 Chat Completions，App 是**唯一写引擎与工作台激活配置的人**。

## 产品交付形态（避免概念混淆）

这里把两个经常被混在一起的问题拆开：

1. **运行时是不是多进程？**
是。桌面 App、codex 引擎、Hermes 引擎、模型网关各司其职，靠子进程 + 协议协作。

2. **用户安装 BlackRain 后要不要自己再装 Agent 环境？**
不需要。**产品态应当是单安装包交付**：把 codex 二进制、Hermes 运行时、CODE 专用网关、默认插件/参考工作台、专属 `CODEX_HOME` / `HERMES_HOME` 模板以及必要运行时资源一起随 app 提供。

3. **安装后新增垂类工作台是否永远零外部依赖？**
不保证。工作台可能携带可合法分发的运行时，也可能要求用户已经拥有 Office、CAD 等商业宿主软件，或引导用户配置数据源和账号。关键不是假装没有依赖，而是由 Manifest 明确声明、由 App 检查和引导，不能让小白手工猜环境。

因此，本项目追求的不是“单二进制单进程”，而是：

> **单安装包交付，零感知外部依赖，多进程内置运行。**

开发态为了迭代速度，允许“本地编译内核 + 手动起网关”；产品态不把这套复杂度暴露给用户。

## 运行时拓扑

下图是定稿目标拓扑。Hermes Desktop 到 WORK surface 的现有合同范围已在 macOS 完成代码级收口，但 Windows Tauri、Hermes/Relay、PTY、Office 和发布矩阵仍未验收；不能把目标图或非 Windows 自动化当成发布证据。

```
┌─ BlackRain（git subtree 自 CodexMonitor，Tauri）─────────┐
│                                                          │
│  前端：工作台货架/项目/任务 + WORK/CODE 执行 surface + 审批/成果   │
│       ↕                                                  │
│  Rust 后端 = 工作台生命周期监工 + 唯一写配置的人             │
│       ├─ 工作台 Manifest / 激活状态 / 权限 / 项目绑定（目标）  │
│       ├─ CODE → codex 内核（子进程·黑盒·原装）              │
│       │        └─读 CODEX_HOME/config.toml → Responses ↓   │
│       │          模型网关（子进程·CODE 专用）               │
│       │        └─responses⇄chat 翻译 → Chat ↓              │
│       └─ WORK → Hermes Agent（子进程·黑盒·原装）            │
│                └─读 HERMES_HOME/config.yaml → Chat ↓       │
└────────────────────────────────────────────│─────────────┘
                                              ↓
                            new-api 计量 → DeepSeek / GLM / Qwen / Kimi ...
```

配置是单行道：**工作台/Providers UI（唯一写入）→ App 生成工作台激活配置 → CODE 写专属 `config.toml` / WORK 写 Hermes `config.yaml` → 引擎读取 → 模型与工具链。** CODE 路径的 `base_url` 指向本地网关；WORK 路径直接使用 Chat Completions。平台 credit 调用的目标中转是 new-api；BYOK 例外与 `.specs/002` 旧 `proxy.py` 链路如何收敛仍是待决，不能把未收敛设计写成已完成事实。

## 四条铁律

1. **两个引擎永远原装黑盒，谁都别改 agent 循环。** codex 管 CODE、Hermes 管 WORK，接国产、防协议废弃、品牌化都落在壳/网关/配置层。能不改就永远白嫖上游更新。
2. **CODE 的协议翻译脏活（responses⇄chat）只锁进专用网关。** 它崩不拖垮界面，协议变化不污染工作台层；今天 Python 原型明天换自研 Rust 版，上层架构零改动。WORK 路径是 Hermes→new-api，零翻译。
3. **App 是唯一写配置的人。** codex 用专属 `CODEX_HOME`，藏在 app 数据目录，绝不碰用户机器原有 `~/.codex`；Hermes 用独立 `HERMES_HOME` / `config.yaml`。详见 [08](08-仓库结构与上游策略.md) 和 [REFERENCES](REFERENCES.md)。
4. **工作台必须声明环境，不依赖作者电脑的偶然状态。** 工具、运行时、宿主软件、账号、权限、验证和卸载都进入工作台协议；当前协议尚未实现，目标边界见 [.specs/008](../.specs/008-expert-workbench-package/)。

## 引擎形态：钉死+自带黑盒（不是 PATH 黑盒）

"黑盒"是两根轴：**行为**（改不改 agent 循环）+ **制品**（二进制/运行时从哪来）。

| 形态 | 行为 | 制品 | 用于 |
|---|---|---|---|
| PATH 黑盒 | 不改 | 用用户机器上的 `codex`（CodexMonitor 现状） | 玩具 ❌ |
| **钉死+自带黑盒** | 不改 | 从钉死的 upstream commit / tag 构建、打包进 app | **v1 ✅** |
| 最小 fork 黑盒 | 仍不改循环，只 patch 品牌/去登录/去遥测/国产默认 | 从 fork 分支构建 | B2B 合规触发时 |
| 硬 fork | 大改 | 自养 97 crate | 永远别 |

MVP 行为上当黑盒成立（接国产在壳外解决），但**制品轴必须升级**：钉版本（可复现、自主决定何时吃上游）、供应链可控、随 app 打包。目标锁定值是 codex `87db9bc` / rust-v0.144.5、Hermes `9de9c25` / v2026.7.7.2；`scripts/fetch-references.sh` 会校验稳定 tag 与完整 SHA 后 detached checkout。源码锁定不等于 Windows 发布验证完成，验收仍看 spec 007。离开黑盒的唯一现实触发点 = B2B 要"可证明零外联"或白标，那时升到**最小 fork**，agent 循环一行不动。

这也意味着：

- v1 不应依赖用户机器上预装的 `codex` 或 Hermes。
- v1 不应要求用户手动准备 `~/.codex` / `~/.hermes`。
- v1 尽量不要求用户另装 Python / Node 之类的外部运行时。

如果某个组件在工程上仍然需要自己的辅助运行时，那也应随安装包一起交付，并由 App 托管，而不是转嫁给用户。

## ⚠️ CODE 网关是硬前置，不是可选的 B 阶段（已实测推翻 A 阶段）

> **2026-06-23 实测修正**：03 文档设想的「A 阶段先用 `wire_api=chat` 直连，B 阶段再上翻译网关」**在当前 6 月内核上已不成立**。`wire_api="chat"` 已被官方彻底删除（见 [codex#7782](https://github.com/openai/codex/discussions/7782)），内核源码硬拒该值（`WireApi` 枚举只剩 `Responses` 一个变体），实测启动会报 `wire_api = "chat" is no longer supported` 并退回默认配置。

含义：**CODE 路径没有「网关槽位为空也能连国产模型」这条捷径。** codex 只会往上游发 Responses 协议，而 DeepSeek/GLM/Qwen/Kimi 只懂 Chat Completions，中间**必须**有 responses⇄chat 翻译。因此：

- **CODE 网关从 M1 起就是硬依赖**，不是 M3 才填的可选件。
- codex 失败方式是**优雅降级**：不崩溃，记 ERROR + 推 `configWarning` 协议通知给壳 → 我们可在 UI 显示「该 provider 配置无效」。
- WORK 路径不走这个网关：Hermes 原生 Chat Completions，直接连 new-api。
- 这反而印证了整体架构：网关这个「可替换小弟」的槽位我们早就留对了，只是它的启用时机从「B 阶段」提前到「M1」。

翻译这件难活的精确卡点是**多轮工具调用历史的忠实转译**——LiteLLM 单回合 OK、多回合因 `tool_calls` 与 `tool_call_id` 配对不当报 400。它是 CODE 可用性的硬基础设施，但不再被视为 BlackRain 的主要市场护城河；核心资产位于工作台层。

## 里程碑

| 里程碑 | 目标 | 验证 |
|---|---|---|
| **M0-CODE** | 壳能 build、拉起 codex、协议探针全绿 | ⚠️ 2026-06-23 的四探针 PASS 是 macOS 历史证据；Windows MVP 仍待 `.specs/007` 实测 |
| **M1-CODE** | Providers 面板 + 专属 CODEX_HOME + **CODE 网关（responses⇄chat 翻译）** | ⚠️ DeepSeek 多轮工具只在 macOS、`STRIP_TOOLS=0` 探针路径通过；App 托管 spawn 当前默认剥工具，修复后还需 Windows 验证 |
| **S1-WORK** | Hermes `/v1` 经 new-api 接国产 Chat 模型，零翻译 | ⚠️ 独立 spike 已验；Windows/Tauri 产品化接入按 [.specs/009](../.specs/009-hermes-work-surface/) 推进 |
| **W0-PACKAGE** | 定义并实现最小工作台 Manifest、依赖检查、激活、健康检查和卸载 | 以 [.specs/008 verification](../.specs/008-expert-workbench-package/verification.md) 为准；当前只有 spec |
| **W1-OFFICE** | Office 参考工作台完成 Windows 安装、任务执行、结果验证和恢复闭环 | 5 场景 × 10 次质量基线；当前未跑 |
| **W2-VERTICAL** | 与真实专家完成第二套市场切入工作台 | 新电脑可复现、真实用户重复使用，垂类与合规边界待决 |
| **M3** | Windows 安全/恢复闭环、专家市场、更多垂类工作台 | 市场和工作室均为 post-MVP；OS 沙箱只有实机验证后才能列为能力 |

对应目录：`apps/desktop`（Core 监工+界面）/ `gateway`（CODE 翻译 sidecar）/ `plugins`（工具适配器）/ `workbenches`（工作台包与参考内容）/ `codex-upstream`（CODE 原装引擎）/ `hermes-upstream`（WORK 原装引擎）。
