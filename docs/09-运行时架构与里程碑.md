# 09 运行时架构与里程碑

> 本文是 [03 系统架构](03-系统架构.md) 的运行时落地版：03 讲"分几层、复用什么"，本文讲"跑起来时有几个进程、谁管谁、怎么换挡"。

## 一句话

桌面 App 是一个**监工**，看管两个长期运行的小弟——codex 内核（干活）和模型网关（翻译）；App 自己是**唯一写配置的人**，所有"接国产模型"的脏活锁在网关进程里，内核保持原装不动。

## 产品交付形态（避免概念混淆）

这里把两个经常被混在一起的问题拆开：

1. **运行时是不是多进程？**
是。桌面 App、codex 内核、模型网关各司其职，靠子进程 + 协议协作。

2. **用户安装后要不要自己再装一堆环境？**
v1 的目标是不需要。**产品态应当是单安装包交付**：把内核二进制、网关、默认插件、专属 `CODEX_HOME` 模板以及必要运行时资源一起随 app 提供。

因此，本项目追求的不是“单二进制单进程”，而是：

> **单安装包交付，零感知外部依赖，多进程内置运行。**

开发态为了迭代速度，允许“本地编译内核 + 手动起网关”；产品态不把这套复杂度暴露给用户。

## 运行时拓扑

```
┌─ 2049 App（fork 自 CodexMonitor，Tauri）─────────────────┐
│                                                          │
│  前端：对话 / diff / 审批 / Providers面板 / 工作台          │
│       ↕                                                  │
│  Rust 后端 = 监工 + 唯一写配置的人                         │
│       ├─ 拉起看管 → codex 内核（子进程·黑盒·原装）          │
│       │                └─读 config.toml 后 HTTP 调模型 ↓   │
│       └─ 拉起看管 → 模型网关（子进程·仅接国产时才起）        │
│                         └─ responses⇄chat 翻译 → HTTP ↓    │
└────────────────────────────────────────────│─────────────┘
                                              ↓
                            DeepSeek / GLM / Qwen / Kimi ...
```

配置是单行道：**Providers 面板（唯一写入）→ 专属 config.toml → 内核读取 → base_url 决定连官方还是连网关。**

## 三条铁律

1. **内核永远原装，谁都别改。** 接国产、防协议废弃、品牌，没一件需要动 agent 循环。能不改就永远白嫖上游更新——这是"忠于上游"卖点的物理保证。
2. **最难的活（responses⇄chat 翻译）锁进可替换的小弟进程。** 它崩不拖垮界面；它最常改（国产 API 老变）不碰别人；今天 ccNexus 明天换自研 Rust 版，上层架构零改动。
3. **App 是唯一写配置的人，且用专属 CODEX_HOME。** 藏在 app 数据目录，绝不碰用户机器原有 `~/.codex`。既不和已装 codex 打架，也消除"Providers 面板 vs 上游抢 config.toml"——两个写入方都是 fork 内自己的代码，协调即可。详见 [08](08-仓库结构与上游策略.md)。

## 内核形态：钉死+自带黑盒（不是 PATH 黑盒）

"黑盒"是两根轴：**行为**（改不改 agent 循环）+ **制品**（二进制从哪来）。

| 形态 | 行为 | 制品 | 用于 |
|---|---|---|---|
| PATH 黑盒 | 不改 | 用用户机器上的 `codex`（CodexMonitor 现状） | 玩具 ❌ |
| **钉死+自带黑盒** | 不改 | 从钉死的 upstream commit 构建、打包进 app | **v1 ✅** |
| 最小 fork 黑盒 | 仍不改循环，只 patch 品牌/去登录/去遥测/国产默认 | 从 fork 分支构建 | B2B 合规触发时 |
| 硬 fork | 大改 | 自养 97 crate | 永远别 |

v1 行为上当黑盒成立（接国产在壳外解决），但**制品轴必须升级**：钉版本（可复现、自主决定何时吃上游）、供应链可控、随 app 打包。离开黑盒的唯一现实触发点 = B2B 要"可证明零外联"或白标，那时升到**最小 fork**，agent 循环一行不动。

这也意味着：

- v1 不应依赖用户机器上预装的 `codex`。
- v1 不应要求用户手动准备 `~/.codex`。
- v1 尽量不要求用户另装 Python / Node 之类的外部运行时。

如果某个组件在工程上仍然需要自己的辅助运行时，那也应随安装包一起交付，并由 App 托管，而不是转嫁给用户。

## ⚠️ 网关是硬前置，不是可选的 B 阶段（已实测推翻 A 阶段）

> **2026-06-23 实测修正**：03 文档设想的「A 阶段先用 `wire_api=chat` 直连，B 阶段再上翻译网关」**在当前 6 月内核上已不成立**。`wire_api="chat"` 已被官方彻底删除（见 [codex#7782](https://github.com/openai/codex/discussions/7782)），内核源码硬拒该值（`WireApi` 枚举只剩 `Responses` 一个变体），实测启动会报 `wire_api = "chat" is no longer supported` 并退回默认配置。

含义：**没有「网关槽位为空也能连国产模型」这条捷径。** 内核只会往上游发 Responses 协议，而 DeepSeek/GLM/Qwen/Kimi 只懂 Chat Completions，中间**必须**有 responses⇄chat 翻译。因此：

- **网关从 M1 起就是硬依赖**，不是 M3 才填的可选件。
- 内核失败方式是**优雅降级**：不崩溃，记 ERROR + 推 `configWarning` 协议通知给壳 → 我们可在 UI 显示「该 provider 配置无效」。
- 这反而印证了整体架构：网关这个「可替换小弟」的槽位我们早就留对了，只是它的启用时机从「B 阶段」提前到「M1」。

翻译这件难活的精确卡点（13 天前另一次实测得出）：**多轮工具调用历史的忠实转译**——LiteLLM 单回合 OK、多回合因 `tool_calls` 与 `tool_call_id` 配对不当报 400。这是产品级翻译代理要攻克的核心，也是潜在护城河。详见记忆 `codex-wire-api-chat-deprecation-risk`。

## 里程碑

| 里程碑 | 目标 | 验证 |
|---|---|---|
| **M0** | 壳能 build、拉起内核、协议探针全绿 | ✅ 已达成（2026-06-23，四探针 PASS）|
| **M1** | Providers 面板 + 专属 CODEX_HOME + **网关（responses⇄chat 翻译）** | **DeepSeek 跑通**（网关是硬前置，非可选）|
| **M2** | 工作台/插件（往 CODEX_HOME 放 skills/AGENTS.md + 管理界面）| 小白能用一个垂类工作台 |
| **M3** | 沙箱、市场 | 按需推进 |

对应目录：`apps/desktop`（监工+界面）/ `gateway`（可替换小弟的槽）/ `plugins`（放进 CODEX_HOME 的文件）/ `codex-upstream`（原装内核）。
