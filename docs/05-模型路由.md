# 05 模型路由

> v1 真实状态(2026-06):**用户在模型广场手动选模型**。自动按任务选模型(Auto-Mode,类 Cursor)是**大后期方向**,MVP 不做。
> 历史的「按任务推荐表 + 各家国产模型速览」已删除——那些表里 99% 的厂商型号都是调研期假设、未在仓库代码里真正接通,留着会让人把方向误读成事实。

## 核心理念:不锁模型

2049 App 没有自家模型要卖,这是相对所有大厂工具的结构性优势。我们把每个国产模型当成「可热插拔的零件」,**让用户自己选**——产品不绑死任何一家模型厂商。

技术前提:几乎所有国产模型都提供 **OpenAI 兼容接口**,换 `base_url + model + key` 即可切换。统一抽象成 OpenAI 兼容客户端,模型广场(`Settings → 模型网关`)由用户自己增删 provider。

## v1 实装

- **官方第一批支持** = DeepSeek `deepseek-v4-flash`(默认) + `deepseek-v4-pro`。
  - 默认 credit 模式走平台代理(持平台 DeepSeek key,按真实 usage 扣 credit);Plus+ 可切 BYOK 走自己 key。
  - 计费 credit 倍率 flash 0.5x / pro 1.5x(比值 = DeepSeek 真实成本比 3:1),详见 [.specs/002 accounts-credits](../.specs/002-accounts-credits/)。
- **模型广场(`Settings → 模型网关`)** = 用户自加任意 OpenAI-compatible provider:base_url + key + 模型列表,启停/测试连接/刷新模型一应俱全。详见 [.specs/001 providers-model-gateway](../.specs/001-providers-model-gateway/)。
- **对话模型选择器** = 数据源仅取自模型广场 registry,用户手动挑模型(不读内核自带 OpenAI 目录,避免选中后报 `response.failed`)。
- **自动按任务路由 = 不做**。M1 决策已固化在 [.specs/001 decisions](../.specs/001-providers-model-gateway/decisions.md):自动路由会扩大范围、掩盖协议翻译问题,先把链路稳定与手动选择做好。

## 大后期方向:Auto-Mode(类 Cursor)

形态参考 Cursor:用户在模型选择器里选「Auto」,系统按当前任务类型(编排/编码/写作/视觉……)自动挑选最合适的模型。

- **触发时机**:至少要先满足两个前提才能做——① 模型广场 registry 里有 ≥2 个真实跑通工具调用的 provider;② 有真实使用数据沉淀「哪类任务跑哪个模型靠谱」(没有真实数据就只能拍脑袋)。
- **MVP 不做,大后期再立独立 spec。** 列在这里只为标记方向,不是开发清单。

## 与内核协议的衔接(运行时硬约束)

Codex 内核默认走 OpenAI 的 **Responses** 协议,而国产模型几乎全是 **Chat Completions**。⚠️**`wire_api="chat"` 直连捷径已被上游删除**(2026-06 在内核 51b3cd5 实测,见 [codex#7782](https://github.com/openai/codex/discussions/7782)):

- **没有 chat 直连捷径**,自带 **Responses↔Chat 转译网关从 M1 起就是硬依赖**,不是可选的后期演进。内核只往上游发 Responses,国产模型只懂 Chat,中间必须翻译。
- 翻译实现见 [gateway/](../gateway/) 与 [09 运行时架构](09-运行时架构与里程碑.md);⚠️ codex 仓库自带的 `responses-api-proxy` 只是转发/调试工具,**不做 Responses→Chat 协议转换**,帮不上国产模型,因此自带产品级转译代理。
- 精确卡点 = **多轮工具调用历史的忠实转译**(`tool_calls`↔`tool_call_id` 配对),这是转译代理的核心难点与潜在护城河。

## 架构落地纪律

- 模型 ID 全局唯一,推荐 `<provider-id>/<model-id>` 格式(早期默认值 `deepseek-v4-flash` 暂留为别名)。
- Provider 做**认证分级**(2026-07-06 定):「官方认证」(实测过流式、多轮工具调用、`apply_patch` 元数据的 provider)与「实验性、自担」两档在 UI 分开标示——`apply_patch` 依赖模型元数据声明、各家工具调用格式各有癖好,「任意 OpenAI-compatible 即可用」对未实测 provider 不成立(接国产模型的硬坑清单见 [codex 底账](../.specs/003-dual-engine-architecture/codex-capability-ledger.md) §五、§七)。
- Provider 配置 / API key / 模型列表是 **BlackRain App + Gateway** 的事,**不进 Codex `config.toml`**——Codex 只看到固定的 `blackrain_gateway` provider。
- 第三方 API key 走系统凭据存储(macOS Keychain / Windows Credential Manager / Linux Secret Service),不落明文、不进普通 `settings.json`。
- 平台代理(credit 模式必经)的平台 key 只存服务端,**绝不下发桌面 App**——「送 token」的硬性物理约束。
- 网关默认只监听本机回环(`127.0.0.1`),不暴露局域网/公网;强制 bearer 校验、不开 CORS。
- B 端私有化时,全部切到自部署开放权重模型(DeepSeek V4 / Qwen / GLM 等开源权重 + vLLM 起 OpenAI 兼容服务),数据零外发。
