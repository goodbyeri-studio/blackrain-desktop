# 05 模型路由

> 本文基于 2026-06 调研。价格/参数多为第三方口径,正式选型前须到各家官方控制台核对;创作能力无权威横评,须自行盲测。

## 核心理念:不锁模型,按任务分流

2049 App 没有自家模型要卖,这是相对所有大厂工具的结构性优势。我们把每个国产模型当成「可热插拔的零件」,按任务自动路由到最合适的那个——用户不需要懂、也不需要选。

技术前提:几乎所有国产模型都提供 **OpenAI 兼容接口**,换 `base_url + model + key` 即可切换。统一抽象成一个 OpenAI 兼容客户端,路由逻辑收在模型路由层。

## 关键的坑

1. **DeepSeek 没有多模态**。它是纯文本/编码/性价比路线。任何生图、生视频、读图需求,必须路由到字节(即梦)或 MiniMax(海螺),不能指望 DeepSeek。
2. **创作能力没有权威横评**。「谁写网文最强」目前全是体感和营销口径。上线前必须用真实题材做盲测(同 prompt 跑 5 家,人工打文笔/情绪/连贯/合规分),再定写作类任务的默认路由。
3. **价格跨源打架严重**(如 GLM-5 输入价从 $0.11 到 $1.00 都有传闻)。做预算前必须官方核对。
4. **聚合网关有合规风险**。Atlas Cloud 之类「一个端点打通多模型」的网关方便,但要评估数据出境和稳定性,B 端尤其敏感。

## 与内核协议的衔接

Codex 内核默认走 OpenAI 的 **Responses** 协议,而国产模型是 **Chat Completions**。⚠️**原设想的「A 阶段先 `wire_api="chat"` 直连」已被上游删除**(2026-06 在内核 51b3cd5 实测:`WireApi` 枚举只剩 `Responses`,喂 `chat` 直接报 `wire_api = "chat" is no longer supported`,见 [codex#7782](https://github.com/openai/codex/discussions/7782))。因此:

- **没有 chat 直连捷径**,自带 **Responses↔Chat 转译网关从 M1 起就是硬依赖**(不是可选的后期演进)。内核只往上游发 Responses,国产模型只懂 Chat,中间必须翻译。
- 网关选型与集成形状见 [09 运行时架构](09-运行时架构与里程碑.md) 及 [08 仓库结构](08-仓库结构与上游策略.md);⚠️ Codex 仓库自带的 `responses-api-proxy` 只是转发/调试工具,**不做 Responses→Chat 协议转换**,帮不上国产模型,需自带产品级转译代理。
- 精确卡点 = **多轮工具调用历史的忠实转译**(`tool_calls`↔`tool_call_id` 配对),这是转译代理的核心难点与潜在护城河。

## 架构落地提示

- 统一抽象成 OpenAI 兼容客户端,路由策略可配置(按任务类型 → 模型)。
- 主控 agent(M3 或 V4-Pro)与兜底/批量(V4-Flash)分离,控成本。
- 视觉、生图、生视频走专用产品 API,不混进主控。
- 网络暴露的路由网关务必加鉴权与速率限制;聚合网关须评估数据出境合规。
- B 端私有化时,全部切到自部署开放权重模型,实现数据零外发。
