# 05 模型路由

> 模型是工作台的可替换执行资源，不是 BlackRain 的核心商品。运行时真实状态以 [.specs/001](../.specs/001-providers-model-gateway/) 和对应 `verification.md` 为准。

## 定位

BlackRain 不自研基础模型，也不把“支持最多模型”作为主要竞争叙事。

工作台作者和平台需要的是：

- 在质量、成本、速度之间选择合适模型
- 在国产模型之间可替换
- 符合国内网络、计费和合规要求
- 模型升级时不破坏工作台协议
- 允许高级用户或企业 BYOK

普通用户购买的是工作台结果，不应被迫理解 provider、协议和倍率。

## 当前双路径

```text
WORK 工作台
  Hermes → Chat Completions → BlackRain Relay(New API) → 国产模型

CODE / 软件开发工作台
  codex Responses → BlackRain Gateway → Chat Completions
                  → BlackRain Relay(New API) → 国产模型
```

- Hermes 原生使用 Chat Completions，WORK 路径不经过协议翻译 Gateway。
- codex 当前只发 Responses；国产模型普遍以 Chat Completions 接入，因此 CODE Gateway 是硬依赖。
- App 是唯一写 `CODEX_HOME` / `HERMES_HOME` 和 provider 配置的人。

完整进程拓扑见 [09](09-运行时架构与里程碑.md)。

## 工作台与模型的关系

工作台可以声明模型需求，但不应把某个商业模型写成不可替换依赖。

建议逐步支持以下声明：

- 最低上下文长度
- 是否需要工具调用
- 是否需要视觉、语音或长文档
- 建议模型档位
- 可接受的 fallback
- 成本预算
- 数据地域或 provider 限制
- 已验证模型矩阵

工作台的 `verification` 必须区分：

- 在什么模型上通过过标准任务
- 换模型后是否重新验证
- 哪些能力只是理论兼容

“OpenAI-compatible” 只说明接口形状相近，不证明工具调用、流式、多轮历史和错误语义完全兼容。

## v1 用户体验

- 默认给普通用户一个平台推荐模型，不让首次使用被模型配置阻断。
- 高级用户可以在模型设置中手动选择或添加 provider。
- 工作台可给出“推荐 / 兼容 / 未验证”模型状态。
- 模型不可用时，先解释原因和降级影响，不静默换到可能改变结果的模型。

## Auto-Mode

自动路由不是 MVP 主线。只有积累真实任务数据后，平台才有依据按以下维度自动选模型：

- 工作台类型
- 任务复杂度
- 工具调用可靠性
- 历史成功率
- 延迟与成本
- 用户预算
- 数据与合规要求

在此之前，“让用户自己选模型”也不能冒充智能路由。

## 当前真实状态

- DeepSeek 已在 macOS 历史探针、显式 `STRIP_TOOLS=0` 条件下驱动 codex 完成真实工具调用。
- App 托管 Gateway spawn 尚未显式设置 `STRIP_TOOLS=0`，普通产品启动路径会剥除工具，是发布阻塞项。
- 多 provider registry 主要有静态和前端测试，真实第二 provider 尚未完整验证。
- Hermes 经 new-api 接 DeepSeek 的独立 spike 已通过，但尚未形成 Windows/Tauri WORK 产品闭环。
- 生产项目边界已冻结为 Desktop→Cloud 获取权益/受限 token，模型数据面进入独立 BlackRain Relay；Supabase 商业账本与 Relay usage/批发账本分离，见 [.specs/010](../.specs/010-three-project-platform/)。具体 broker、对账和 BYOK 仍待实现与决策。

## 原则

1. 模型可替换，工作台资产不可绑定单一厂商。
2. 普通用户看到任务和结果，高级用户才看到 provider 细节。
3. 模型兼容必须通过真实工作台任务验证。
4. 不把云模型宣传成全程本地；推理内容会发往用户选择的模型链路。
5. 不锁模型是平台卫生标准，不是足以单独抵御大厂的护城河。
