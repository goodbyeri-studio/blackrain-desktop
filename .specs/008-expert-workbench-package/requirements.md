# Requirements

> **事实状态纪律**：本 spec 当前定义目标协议，尚无完整实现。必须始终分开：①目录、Manifest 或代码存在；②Windows 运行验证通过；③第三方工作台可安全发布和交付。不得把本设计文档当成已实现证据。

## 背景

2026-07-12，BlackRain 的产品定位从“面向非开发者的通用桌面 Agent”重构为“AI 驱动的垂类工作环境平台”。核心商品不再是散装 Skill 或插件，而是可安装、可维护、可验证的专家工作台。

当前仓库已有：

- `plugins/office-cli/` 工具和 Skill 骨架
- `workbenches/office-agent/` Office 内容骨架
- Tauri bundle 的部分资源映射
- Hermes/codex 两套执行引擎设计

但尚未有统一工作台 Manifest、依赖解析、安装、升级、回滚、卸载、权限预览、包签名和验证协议。

## 用户目标

### 工作台使用者

- 作为不懂环境配置的普通用户
- 想安装一套领域专家配置好的工作环境
- 成功后可以直接创建项目、选择任务并由 AI 使用已配置工具完成工作
- 不需要手工猜测 Python、Node、PATH、MCP、模型或目录配置

### 领域专家

- 作为拥有成熟工具链和工作方法的专家
- 想把自己的数字工作环境转成可重复交付的产品
- 成功后能声明工具、方法、模板、数据连接、验证和适用边界

### 工作台封装者

- 作为帮助专家产品化环境的人
- 想用稳定格式描述依赖、权限、安装、任务和验证
- 成功后可以在干净 Windows 环境重复构建、安装和测试工作台

### 平台维护者

- 作为 BlackRain Core 维护者
- 想安全管理工作台的安装、激活、升级、回滚和卸载
- 成功后能解释每个文件、进程、权限、网络连接和 License 的来源

## 核心定义

工作台是面向一个岗位、领域或任务体系的可复现数字工作环境：

```text
Skill + 插件 + 环境 + 资源 + 验证 + 任务入口
```

工作台包是静态声明与受控资源的集合；用户项目是安装后产生的运行实例。升级或卸载工作台不得默认删除用户项目数据。

## 非目标

- 本阶段不开放任意第三方在线市场。
- 本阶段不实现工作室/OPC 多工作台协作。
- 本阶段不允许工作台修改 codex/Hermes Agent 循环。
- 本阶段不承诺跨 Windows/macOS/Linux 的统一制品；MVP 只验 Windows x64。
- 本阶段不自动复制作者电脑上的商业软件、私有数据、Cookie、密钥或无权再分发的文件。
- 本阶段不定义金融、医疗、法律等领域的完整业务合规，只定义包级声明入口。
- 不把“目录中存在 `workbench.yaml`”等同于可安装或可发布。

## 功能需求

### R1：Manifest

每个工作台必须有机器可读 Manifest，至少声明：

- id、名称、版本、作者、描述
- 面向岗位/领域和标准任务
- 支持的平台、架构和 BlackRain Core 版本
- Skills、插件和资源
- 工具、运行时和宿主软件依赖
- 账号、密钥和数据源槽位
- 文件、进程、网络和系统权限
- 安装、健康检查、升级、回滚和卸载入口
- 验证矩阵、已知风险和支持渠道
- License、来源和不可再分发依赖

### R2：依赖类型

依赖必须显式分类：

1. `bundled`：包内合法随附。
2. `managed`：由 BlackRain 从声明来源下载并校验。
3. `system`：要求系统或用户已有，例如 Office/CAD。
4. `user-provided`：账号、License、API key、数据文件。

每个依赖必须声明版本、来源、完整性、License、安装范围和卸载策略。

### R3：安装计划与审批

安装前必须向用户展示：

- 将安装或下载什么
- 占用空间
- 访问哪些目录和网络域名
- 是否启动后台进程
- 需要哪些商业软件、账号和密钥
- 哪些文件不会在卸载时删除
- 风险和数据出境说明

用户确认后才能执行会改变系统状态的步骤。

### R4：隔离和路径

- 工作台版本化资源放在 BlackRain App data 下的受控目录。
- 用户项目放在用户选择或创建的工作目录。
- 工作台升级不得覆盖用户项目。
- 多版本共存或升级回滚所需状态必须可追踪。
- 不得默认修改用户全局 `~/.codex`、全局 Python 或系统 PATH。

### R5：激活

Core 激活工作台时，负责把声明的 Skills、插件、环境变量、项目模板和权限映射给选定执行引擎。

工作台不得直接成为引擎配置的第二写入者。

### R6：验证

工作台至少提供：

- 安装后健康检查
- 工具版本和可执行性检查
- 一个不使用敏感真实数据的标准任务 smoke
- 输出结构或结果断言
- 失败时的诊断信息

发布级工作台还需提供真实领域任务评测和兼容矩阵。

### R7：升级、回滚和卸载

- 升级先构建新版本，再原子切换激活状态。
- 新版本健康检查失败时回滚旧版本。
- 卸载只删除工作台受控资源，默认保留用户项目。
- 依赖被多个工作台共享时不得误删。
- 卸载后应报告残留项和保留原因。

### R8：来源、License 和签名

- 包内每个第三方制品必须可追溯到来源和 License。
- 无权再分发的制品只能作为系统依赖或用户提供依赖。
- 市场阶段必须支持作者身份、包签名和完整性校验。
- MVP 官方包至少需要构建期 checksum 和来源清单。

## 成功标准

### 代码/配置存在

- `workbench.yaml` schema 或等价机器可读 schema 存在。
- Core 有 inspect / plan / install / activate / verify / uninstall 的接口骨架。
- Office 参考工作台迁移到新格式。

### 验证通过

- 在干净 Windows x64 环境安装 Office 参考工作台。
- 安装计划、权限预览、依赖检查和健康检查可见。
- 创建新项目并完成至少一个真实 Office 任务。
- 升级失败可回滚。
- 卸载不删除用户项目，受控资源按声明清理。

### 发布/交付可用

- NSIS 安装后的 BlackRain 可以安装、运行和卸载官方工作台。
- 包内第三方来源、License、checksum 和 NOTICE 完整。
- SmartScreen/签名、失败降级和诊断路径经过真实 Windows 验证。
- 公开第三方市场需另行完成包签名、审核、权限和结算 spec。

## 安全与合规

- 安装脚本不得默认以管理员权限运行。
- 需要提权时必须单独说明原因和影响。
- 密钥进入系统凭据存储，不写 Manifest、日志或项目模板。
- 网络域名和数据流必须声明。
- 工作台不能借宿主 Agent 绕过用户审批。
- 金融、医疗、法律等高责任工作台需要额外类别策略。

## 开放问题

- [ ] Manifest 使用 YAML、TOML 还是 JSON Schema 驱动的 YAML。
- [ ] 工作台包扩展名和压缩格式。
- [ ] 插件依赖采用引用、内嵌还是两者并存。
- [ ] 运行时共享缓存的引用计数和垃圾回收策略。
- [ ] 官方包与第三方包的签名根和信任策略。
- [ ] 用户修改工作台内容后的升级和 fork 语义。
- [ ] 工作台如何声明推荐模型、兼容模型和评测结果。
- [ ] 高责任领域的审核、免责声明和功能限制。
