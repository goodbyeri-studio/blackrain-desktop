# Decisions — GUI 重做

## 2026-07-11:范围包含前端功能对齐,MVP 只验收 Windows

- 决策:本 spec 既包含 token/视觉/DS,也包含搜索、导航历史、侧栏层级等为复刻 CODE UX 必需的前端交互;不新增内核协议。MVP 只在 Windows 实机验收,macOS/iOS 属 post-MVP/上游资产。
- 原因:旧口径「纯视觉」与 tasks 中的搜索、导航、侧栏状态任务相互冲突;Windows-only 已是 MVP 平台决策。
- 影响范围:`requirements.md`、`design.md`、`tasks.md`、`verification.md`、`codex-ui-copy-checklist.md`。
- 后续复查条件:post-MVP 启动其他平台时,新增对应实机验收矩阵。

## 2026-06-26：复刻 = 重建设计语言，而非照搬资源字节（第一法律）

- 决策：本 spec 的「照着原版复刻」严格限定为**复刻设计语言**（布局/间距/配色/字阶/交互态），在 BlackRain 自己的 design-system 里重实现；**绝不**复制 OpenAI 的图标 SVG path 字节、字体文件、private path 源码/bundle。
- 原因：BlackRain 是闭源商业 B2B 产品。Codex app 是 OpenAI 专有资源，照搬字节 = 侵权，摧毁商业基础。设计语言（间距节奏、色彩层级）属于可观察、可独立重实现的范畴，重绘合法。
- 替代方案：① 逐字节抄（法律死刑，否决）；② 完全原创不参考（放弃商业级标杆，慢且无保证）。取中间：参考语言、自主重建。
- 影响范围：所有图标/字体/视觉资源的引入方式；每个新增资源须记来源。
- 后续复查条件：任何一次「为了更像而想直接拿原版文件」的冲动出现时，回看本条。

## 2026-06-26：参考像素默认由人提供，agent 负责量化落地

- 决策：Codex app 为登录态产品，agent 无法稳定抓取计算样式。范本截图/录屏由莓莓提供，agent 负责量化成 token 表并在 DS 落地。
- 原因：分工匹配能力边界——人能进产品截图，agent 擅长把像素量化成可维护的 token 与代码。
- 替代方案：agent 自行抓取（不可行，需登录）；纯凭记忆描述（不可靠）。
- 影响范围：阶段 1 依赖莓莓供图，是工程节奏的输入约束。
- 后续复查条件：若找到可公开稳定访问的 Codex 参考面，可放宽。

## 2026-06-26：对齐不牺牲功能与「无渲染动效」纪律

- 决策：视觉对齐让位于可用性与既定 UI 纪律。若对齐改动致交互回归则回退；Codex 若有入场/位移动画，只取静态视觉，不引入动效（遵守 memory「BR UI零渲染动效硬规则」）。
- 原因：商业级首先是「稳重好用」，不是「动得花哨」；功能回归比不够像更致命。
- 替代方案：为像素一致牺牲功能/引入动效（否决）。
- 影响范围：所有界面对齐的取舍优先级。
- 后续复查条件：硬规则若调整再议。

## 2026-06-26：目标 = 神似（骨/皮/内容三层），保留 BR 玻璃噪点皮肤

- 决策：GUI 拆三层——**骨架**（布局/间距/字阶/组件形态/信息架构/交互模式）尽力模仿 Codex；**皮肤**（毛玻璃/半透明/全息噪点）保留 BR 独有，不抄 Codex 纯色；**内容**（导航项/品牌/模型名/项目/权限文案）保留 BR 身份。目标是「同级精致 + 保留 BR 自我」，不是逐像素一致。
- 原因：Codex 的「商业级」来自结构克制（间距规整、层级清晰），不是来自纯黑背景——克制用玻璃皮肤照样实现。玻璃噪点是 BR 的独有风格质感，是品牌识别度，砍了就丢了自我。
- 替代方案：① 逐像素全抄含纯黑背景（丢 BR 风格，否决）；② 完全自创不参考（丢商业级标杆，否决）。
- 影响范围：每个对齐决策都用「这是骨/皮/内容哪一层」来判断该模仿还是该保留。
- 后续复查条件：若玻璃皮肤实测损伤可读性/高级感，回看下条硬约束。

## 2026-06-26：玻璃/噪点皮肤的硬约束——清晰优先

- 决策：保留玻璃半透明 + 噪点，但**必须克制**：文字对比拉够、边缘清晰。任何一处皮肤导致文字发糊/边缘发脏，降透明度或加底色，清晰优先于质感。
- 原因：Codex 高级感部分来自「不透明实色 + 高对比文字 + 清晰边缘」。玻璃+噪点做过头会发糊发脏，反而干掉想要的高级感。皮肤要服务清晰，不能盖过清晰。
- 替代方案：无约束地堆玻璃噪点（有损可读性，否决）。
- 影响范围：所有用玻璃材质的面板/弹层/composer。
- 后续复查条件：每个玻璃界面验收时核文字对比与边缘。

## 2026-06-26：权限砍到 3 档（去掉「自定义 config.toml」）

- 决策：权限弹层只做 3 档——请求批准 / 替我审批 / 完全访问；**砍掉 Codex 的第 4 档「自定义 (config.toml)」**。pill 按档变色（完全访问=橙色警示）。
- 原因：「自定义 config.toml」是给开发者的逃生口，与 BR「面向非开发者」定位冲突。**砍的是 UI 选项，不是能力**——底层 CODEX_HOME/config.toml 机制照旧，只是不把这个口子暴露给小白。
- 替代方案：照搬 4 档（暴露开发者概念给非开发者，否决）。
- 影响范围：权限弹层 UI；底层配置不变。
- 后续复查条件：若未来面向开发者开高级模式，再议是否放出第 4 档。

## 2026-06-26：模型菜单两级，档位轴随模型真实能力动态显隐

- 决策：抄 Codex 两级菜单形态（推理档 × 模型族），但**档位轴 = 各模型官方真实档位**。DeepSeek = 低/中/高（3 档，已核官方文档）；**某模型无推理档则整个二级档位栏不显示**（不留「暂时不可用」死格子）。不照搬 Codex 的「超高」。
- 原因：档数应由 BR 模型真实能力定，不由 Codex 截图定。留常驻灰的死档子「太蠢」（用户原话）。
- 替代方案：① 照搬 4 档含常驻灰的超高（蠢，否决）；② 显示「暂时不可用」（仍是死格子，否决）。
- 影响范围：模型菜单前端（005）+ 网关 reasoning_effort 透传与模型能力表（001）。
- 后续复查条件：新增模型时更新能力表；档位轴随之变。

## 2026-06-26：两级模型菜单是跨 spec 依赖（005 画壳，001 透传）

- 决策：模型菜单的「推理档」要真生效，必须 005（前端形态）+ 001（网关接 `reasoning_effort` + 模型能力表）一起做。网关现状只在响应侧翻译 `reasoning_content`，请求侧不读不转。
- 原因：只做前端不做网关 = 假菜单，点了不生效，传不到 DeepSeek。
- 替代方案：先只做前端壳（明确标注「未通」，留 TODO）——可作为分阶段交付，但不可当成「已完成」。
- 影响范围：双向标注 005 与 001；网关改动归 001。
- 后续复查条件：网关透传落地后，在 verification 标 PASS。

## 被推翻的方案

### 2026-06-26：吸收 Hermes Desktop 前端以省去自研 GUI

- 原方案：把 Hermes Agent 自带的 Desktop GUI 组件吸收进来，省自研前端成本。
- 为什么推翻：实测 Hermes GUI 过于简陋，远未达商业级；而 BlackRain 壳（CodexMonitor fork）骨架已完整，真正缺的是商业级视觉。吸收简陋 GUI 是负优化。
- 替代方案：保留 CodexMonitor 骨架，以 Codex app 为视觉范本对齐到商业级（本 spec）。
