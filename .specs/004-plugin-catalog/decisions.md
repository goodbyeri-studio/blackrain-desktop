# Decisions

> **状态（2026-07-26）：暂停。** 旧 Office MVP 和供给侧优先级已失效；恢复条件以 docs/06 为准。

## 2026-07-11:目录是 post-MVP 终局参考,Windows office MVP 不实现全目录

- 决策：~34 打包单元只作长期插件供给账本；MVP 只发行 Windows 客户端，并用 Office 参考工作台验证工作台底座，不启动全目录实现。
- 原因:目录广度是终局供给策略,不能挤占当前 Windows 落地与工作台包验证。
- 影响范围:`requirements.md` / `design.md` / `tasks.md` / `verification.md` 都必须把「候选目录」与「已实现/已可发行」分开。
- 后续复查条件:office MVP 完成 Windows E2E 与工作台任务执行验证后,再按真实垂类需求拆分实现 spec。

## 2026-07-11：GPL 候选关闭，LGPL 单独审计

- 决策：Blender 等 GPL 组件只能作为仓库外的架构参考，不能进入 BlackRain 仓库、安装包或产品依赖；3D headless 能力必须另选 MIT/Apache/BSD 等宽松许可证引擎或自行实现。FFmpeg 的 LGPL build 可继续作为候选，但进入发行包前必须完成链接方式、可替换性、许可证文件和最终制品审计。
- 原因：根 `AGENTS.md` / `CONTRIBUTING.md` 已把 GPL/AGPL/BSL/无许可证列为闭源商业产品红线，不能在单功能 spec 里重新打开；LGPL 的义务与 GPL 不同，应单独判断。
- 影响范围：D 类 `3d-headless` 选型、A 类 `media-ffmpeg` 打包配方、requirements/tasks/verification 的合规口径。
- 后续复查条件：只有全仓许可证政策经明确决策改变时，才可重议 GPL；FFmpeg 每次换 build 或版本都要重做制品审计。

## 2026-06-26：插件按「引擎/格式适配器」切，不按任务切

- 决策：插件 = 一个引擎/格式适配器 + 其原生操作族 = 一个 MCP server = 一个 `@`。任务级的东西(转竖屏/改图框/出门窗表/周报)是 skill 配方，住工作台层，不占插件编制。
- 原因：用 OS 心智模型(底座=内核、插件=apt 包、工作台=项目、配方=脚本)——没人 `apt install 把视频转竖屏`，只装 `ffmpeg` 再用脚本组合。按任务切会让插件数爆炸且无法维护；按引擎切把数量锁在 ~34，覆盖面靠数百配方扩展。
- 替代方案：按任务/按用户场景切(朋友初版倾向「门户填报插件」这类)——被否，因为它们无新运行时。
- 影响范围：`plugins`/`workbenches` 目录规范、市集分类。
- 后续复查条件：出现一个无法用现有引擎组合表达的新引擎/新格式时，才加插件。

## 2026-06-26：[铺] 无头开源 / [控] 宿主门控 是打包层的硬切分线

- 决策：每个打包单元标注 `[铺]`(无头开源，进本地胖包，触达 100% 用户)或 `[控]`(需用户已装正版宿主软件，只触达装了的人)。撒网顺序 = 横向[铺] → 纵向[铺] → [控] 垫底。
- 原因：这条线直接决定本地胖包的 reach。把 `ezdxf`(无头，给所有人)和 `AutoLISP`(要 AutoCAD)揉一个包，会让该包要么强依赖 AutoCAD(对没装的人 reach=0)，要么内部其实是两个模块(那就该拆)。
- 替代方案：按领域揉成一个「CAD 插件/财务插件」(朋友版)——被否，会砸全量铺战略。
- 影响范围：CAD/BIM/GIS/设计/影音/ERP 全部一拆为二(1[铺]+≤1[控])。
- 后续复查条件：某 [控] 引擎出现可商用的无头开源替代时，可新增 [铺] 包。

## 2026-06-26：与「26 插件版」的分歧裁决

- 决策：以合并版(7 浏览类 × ~34 打包单元)为准，对朋友 26 版做四处修正：
  1. **补 `desktop-auto`**：Windows UI Automation 是独立于 browser-auto 的真引擎，驱动 GUI-only 本地软件(用友/金蝶桌面端、政务客户端)，下沉刚需，朋友版漏了。
  2. **留 `asset-fetch`**：搜图/生图/扒公开数据是 [04] 白纸黑字标的「自建关键缺口」(让 AI 自己找食材)，朋友版丢了，必须留。
  3. **拆 `hl7-fhir` ✂ `dicom`**：前者文本报文(hl7apy)，后者二进制影像(pydicom)，零共享运行时，朋友版揉成「医疗插件」是错的。
  4. **CAD/BIM/GIS/ERP 一致地按 [铺]/[控] 拆**：朋友版在 PS/Premiere 上已经拆对了(设计软件 vs 图像、音视频专业 vs 媒体)，却在工程/财务上揉死，自相矛盾，统一拆开。
- 原因：朋友把货架分类(领域)做对了、还逮到 desktop-auto；我们把打包线(运行时+license)划对了、捡回 asset-fetch。两版合并 = 货架按领域 + 打包按运行时。
- 影响范围：design.md 全量目录。

## 2026-06-26：门户填报 = 工作台，不是插件；SCADA 控制端不做

- 决策：①「政务/学校/平台门户填报」无新运行时(= browser-auto + desktop-auto + ocr-vision 编排 + 站点配方)，定位为一等公民工作台，不占插件编制。② 工业 SCADA/PLC **只做 historian-read 只读报表，控制端写入不做**。
- 原因：① 守粒度铁律(无新引擎→不是新插件)；② 控制端写入是工业安全红线，LLM agent 不该碰。
- 影响范围：B 类货架注记、E 类 historian-read 标「只读」。
- 后续复查条件：控制端永不做(安全红线)。

## 2026-06-26：验证层是横切能力、不是闸门——调和「先广撒网」与「验证护城河」

- 决策：两个决定分属两层，不冲突——**目录/撒网(reach-first)决定「造哪些、什么顺序」，不按验证成本过滤，无头开源全造；验证层决定「造出来怎么让人信」，是横切能力，按垂类验证成本伸缩力度，不决定哪个插件存在。**
- 原因：用户 2026-06-26 拍板「先广撒网、不按验证成本过滤」，同时拍板「验证层升级为一等公民」。这两条只有放在不同层才同时成立：撒网管「存在性与顺序」，验证管「交付时的自证强度」。
- 力度分档：低(网文/媒体/文件)= 可视化+抽检；中(数据/CAD几何/PDF提取)= dry-run+diff+抽样；高(财务/XBRL/汇总)= 引擎自检断言(账平/schema)+强制人工确认。
- 影响范围：关联 [03 系统架构](../../docs/03-系统架构.md) 新增 ④验证层、[07 护城河](../../docs/07-护城河与风险.md) 护城河 D。
- 后续复查条件：若某垂类验证成本经实测远超预期(脚手架做不出来)，则该垂类降优先级，但不从目录删除。

## 2026-06-26：GPL/LGPL 引擎候选路线（已被 2026-07-11 决策收窄）

- 当时方案：把 Blender(GPL) 独立进程与 FFmpeg LGPL build 一并保留为候选路线，等待法务和制品审计。
- 收窄原因：后续全仓许可证红线已经明确，GPL 不再是可进入产品的待决项；只有 LGPL 路线继续保留审计空间。
- 当前替代：Blender 仅作仓库外参考；3D headless 另选宽松许可证实现。FFmpeg LGPL build 仍须逐版本审计。

## 被推翻的方案

### 2026-06-26：「每个垂类做成一个揉死的领域插件」

- 原方案：朋友初版「一个 CAD 插件/一个财务插件/一个医疗插件」按领域揉成单包(共 26 个)。
- 为什么推翻：揉死违反「运行时+license 切分线」，砸全量铺战略；且朋友自己在 PS/Premiere 上已拆对，逻辑不自洽。
- 替代方案：领域只用于货架浏览，打包按运行时拆(1[铺]+≤1[控])，得 ~34 单元。
